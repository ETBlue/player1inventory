## Global Components

One-time structural components that appear once in the app shell.

**`Layout`** (`src/components/global/Layout/Layout.tsx`) — root shell that wraps every page. Uses a CSS grid layout (`h-dvh grid grid-cols-[auto_1fr]`):
- Column 1: Sidebar (desktop only, `hidden lg:flex`, `w-56`)
- Column 2: inner grid (`grid-rows-[1fr_auto]`) — main content area on top, Navigation on bottom
- Main element uses `[container-type:size]` enabling `cqh`-based container queries in children
- **One height rule: only `Layout` uses a viewport unit (`h-dvh`).** Every page sizes itself to `<main>` with `h-[100cqh]` or `min-h-[100cqh]`, never `h-screen`, `min-h-screen` or a `vh` / `svh` / `lvh` / `dvh` height. On iOS in home-screen mode `100vh` can be taller than `100dvh`, and when the bottom nav shows, `main` is shorter than the viewport. In both cases a `100vh` page gives empty space at the bottom (`docs/global/bugs/2026-11-24-bug-page-height-vh.md`). `src/lib/pageHeightRule.test.ts` reads every non-test, non-story source file and fails with the file, line and class of each break. Stories are not checked: they have no `Layout`
- A skip-to-main-content link is rendered inside a `<header>` landmark before the sidebar

**`Navigation`** (`src/components/global/Navigation/Navigation.tsx`) — mobile-only bottom navigation bar (`lg:hidden`). Renders 4 nav links (Pantry, Shopping, Cooking, Settings) in a `grid-cols-4` row. Hidden on fullscreen pages: there the component renders `null`, and no padding is added to the page. One function decides which pages those are: `isFullscreenPage(pathname, { desktop })` in `src/lib/layoutRules.ts`, called by `Layout`, `Sidebar` and `Navigation`. Change the rule there, not in a component. `desktop` is required and comes from `useIsDesktop()` (`src/hooks/useIsDesktop.ts`, the Tailwind `lg` width):

| Page | Desktop | Mobile |
| --- | --- | --- |
| `/onboarding`, `/items/*` | full-screen | full-screen |
| household detail pages (`/settings/household/<section>/<id>…`) | full-screen | full-screen |
| `/settings` and every household list page (`/settings/household`, `/settings/household/<section>`) | sidebar shown (`/settings` itself redirects to `/settings/household`) | **full-screen** |
| every other page (`/`, `/shopping…`, `/cooking`) | sidebar shown | bars shown |

**Every settings page is full-screen on mobile since 2026-11-23** (owner request): no bottom bar, and each page has its own Back icon in its top bar. Until then only the tags, vendors, recipes and shelves lists were; `/settings`, `/settings/household`, Locations, Members and Activity kept the bottom bar. `isSettingsPage(pathname)` in the same file is true for `/settings` and everything below it. So the bottom bar's Settings tab is never shown active any more (its active check is still in `Navigation`, harmless). Which Back each page has:

| Mobile page | Back | Where it goes |
| --- | --- | --- |
| `/settings` (the accordion) | **Back** icon (`navigation.back`), new | `useBackToAppPage()`: the last Pantry, Shopping or Cooking page, the same as the desktop household sidebar's Back. This page is the mobile copy of that sidebar |
| `/settings/household` (General) | **Go back** icon (`common.goBack`, `lg:hidden`), new | `useAppNavigation('/settings')`: the previous page, usually the `/settings` menu. The same Back as the other list pages |
| Members, Activity, Locations, Shelves, Vendors, Recipes, Tags lists | their own **Go back** icon (`lg:hidden`), unchanged | `useAppNavigation('/settings')` |
| detail pages (`…/<section>/<id>`) | their own back, unchanged | unchanged |

No page has two Back buttons: the sidebar (with its Back) is not rendered on a full-screen page.

`isHouseholdSettingsPage(pathname)` in the same file is true for `/settings/household` and `/settings/household/<section>` only. **Tests:** `src/test/setup.ts` mocks `matchMedia` as always `false`, so every test renders the mobile layout. Call `mockScreen({ desktop: true })` from `src/test/viewport.ts` to test the desktop one.

**`Sidebar`** (`src/components/global/Sidebar/Sidebar.tsx`) — desktop-only left sidebar (`hidden lg:flex flex-col w-56`). Same fullscreen-page suppression as Navigation (returns `null`, so fullscreen pages have no switcher either). Top to bottom: "Player 1 Inventory" `<h1>`, the `LocationSwitcher` with `variant="full"` (desktop home of the active-location selector — the page toolbars carry the `lg:hidden` compact copy), then the 3 **location-aware** nav links (Pantry, Shopping, Cooking) with icon + label side-by-side. Active: `text-foreground-emphasized bg-background-elevated`.

**🏠 the household entry is pinned to the bottom**, in its own block (`mt-auto`) below the three. It links to `/settings/household`. Its label is `HouseholdLabel` (`src/components/settings/HouseholdLabel/`): the household's name in cloud mode, "My data" (`settings.household.title`) in local mode and while the name loads (households H3a task 3.13). The label is passed to the shared link renderer as its optional second argument and truncates, because a household name can be 100 characters long. It is global, not location-aware, so it is kept away from the switcher and the routes the switcher scopes. Both blocks share one link renderer, so it has the same styling, icon size and active-state logic. Below it is the 👤 user entry: a **button**, not a link, labelled by `UserLabel` ("Preferences" in local mode and E2E cloud mode, the Clerk user's name in real cloud mode, "Preferences" again when that name is empty). Pressing it swaps in **`UserSidebar`** (`Sidebar/UserSidebar.tsx`): one row with the Back icon and a heading with the same label, then `UserSettingsPanel compact`. Back shows only its `ArrowLeft` icon; its accessible name is still "Back" (`aria-label={t('navigation.back')}`). The open state is `useState` in `Sidebar` — no route, a reload closes it, opening it does not navigate. **Any pathname change closes it** (adjust-state-during-render, so no frame shows it on the new page); a search-string change does not. Focus moves to Back on open and back to the 👤 button on Back.

**`UserSettingsPanel`** (`src/components/settings/UserSettingsPanel/`) is the 👤 content, shared by `UserSidebar` and the mobile `/settings` accordion so the two cannot drift: an Account card (real cloud: name, email, last sign-in, account created, via `formatDate`; E2E cloud: the test user id; local: none), then `ThemeCard`, `LanguageCard`, `DataModeCard`. Clerk's `useUser()` is called only inside its `…WithUser` children, which render only in real cloud mode — `useUser()` throws without a `ClerkProvider`, and local mode and E2E cloud mode have none (plan P8, the same split as `DataModeCard`). The mobile `Navigation` bar does **not** mirror this: it still has a Settings tab to `/settings`.

**Two views, chosen by the URL.** When `isHouseholdSettingsPage(pathname)` is true (`/settings/household` and its five list pages), `Sidebar` renders **`HouseholdSidebar`** (`Sidebar/HouseholdSidebar.tsx`) inside the same `<nav>` instead of the main view. It has no app title and no `LocationSwitcher`. Top to bottom:

- **Back** and the heading share ONE row (since 2026-11-23): Back shows only its `ArrowLeft` icon (`size="icon"`), and its accessible name is still "Back" (`aria-label={t('navigation.back')}`), so role queries by name keep working. It goes to `lastAppPage(loadNavigationHistory())` from `src/lib/layoutRules.ts`: the newest `/`, `/shopping…` or `/cooking` URL in `app-navigation-history`, with its search string, or `/` when there is none. It pushes the full URL string with `router.history.push`, like `useAppNavigation`.
- the heading `HouseholdLabel`, an `<h2>` next to the Back icon: the household's name in cloud mode, "My data" (`settings.household.title`) in local mode and while the name loads. A long name wraps inside its own column (`min-w-0 flex-1 break-words`), so it never widens the 224px sidebar and never pushes the icon away
- six links: General, Locations, Shelves, Vendors, Recipes, Tags. In cloud mode a seventh, **Members**, is second (households H5b task G.9). It has `cloudOnly: true` and local mode filters it out, because local mode has no members (design, *Local mode*). **Activity** is eighth, after Tags (households H6 task J.6). It has `cloudOnly: true` and `readsActivity: true`: it shows only when `usePermissions().canReadActivity` is true, so to a household owner or manager in cloud mode. A member and local mode do not see it. Because of `usePermissions`, a test or story of `HouseholdSidebar` needs a `QueryClientProvider` (local mode reads the location list through TanStack Query). Active state comes from TanStack's own match (`activeOptions` + `activeProps`), so `aria-current="page"` and the active styling cannot disagree. General uses `exact: true`, so it is active only on `/settings/household` itself. Last comes item 9, **`HouseholdSwitcher`** (households H7 task L.4): a button, not a link, shown in cloud mode for every household role and not in local mode. Since 2026-11-23 it is NOT in the link list: it has its own block, a direct child of the `<nav>`, pinned to the bottom with `mt-auto` (like the 🏠 and 👤 block of the main sidebar). The `<nav>` is a flex column at least as tall as the screen (`min-h-[100cqh]`; the sidebar is in no size container, so `cqh` means the viewport), inside the `overflow-y-auto` column of `Layout`. So with few links the switcher sits at the bottom of the screen, and with many links the whole panel scrolls and the switcher comes after them. See *HouseholdSwitcher* below.

The five list pages keep their own Back button on mobile only (`lg:hidden`), because on desktop the sidebar has Back.

## Shared Components

Reusable across multiple features and pages.

**`LayoutInnerPages`** (`src/components/shared/LayoutInnerPages/index.ts`) — shared layout for all level 2+ pages (entity detail + new-entity pages). Provides a fixed top bar (back button with `goBack()` default, optional `icon`, `title`, optional `toolbarEnd`) and a scrollable `children` area. Props: `title: ReactNode`, `icon?: ReactNode`, `onBack?: () => void`, `toolbarEnd?: ReactNode`, `children: ReactNode`.

**`Toolbar`** (`src/components/shared/Toolbar/index.tsx`) — shared wrapper for list-page toolbars. Provides `bg-background-surface`, `border-b-2 border-accessory-default`, `px-3 py-2`, `flex items-center gap-2`. Used by shopping (cart toolbar), vendor list, and tags pages. Accepts optional `className` for layout overrides (e.g. `justify-between`, `flex-wrap`).

**`AddNameDialog`** (`src/components/shared/AddNameDialog/index.tsx`) — generic name-input dialog used by Tags, Vendors, and Recipes tabs for inline entity creation. Props: `open`, `title`, `submitLabel`, `name`, `placeholder?`, `onNameChange`, `onAdd`, `onClose`, `isPending?`. Cancel button uses `neutral-outline`. Name input is `autoFocus`. Submit button shows a loading spinner and is disabled when `isPending` is true or when `name` is empty; Enter key is also blocked in both states.

**`LoadingSpinner`** (`src/components/shared/LoadingSpinner/LoadingSpinner.tsx`) — centered animated spinner for page-level loading states. No props. Renders `Loader2` icon (`size-8 animate-spin [transform-box:fill-box] text-foreground-muted`) inside a `flex min-h-[50cqh] items-center justify-center` container (half the height of Layout's `<main>`; it was `min-h-[50vh]` until 2026-11-24). `[transform-box:fill-box]` is required on all `animate-spin` SVG icons — without it Firefox rotates on the Y axis instead of Z when an ancestor has `container-type:size`. Used in pantry page, item detail, and item log tab.

**`ReadOnlyNote`** (`src/components/shared/ReadOnlyNote/ReadOnlyNote.tsx`) — one muted line with an `Eye` icon that says why a page has no add, edit or delete controls (households H5 task F.5). Props: `text?` (default `settings.catalogReadOnly`, "Only a household owner or manager can add or change these."), `className?`, `id?`. Give it an `id` when disabled controls should say why: the cart and cooking pages give the location view-only note an id from `useId()`, and their disabled checkboxes and amount buttons name it in `aria-describedby` (through `ItemCard`'s `controlsDescribedBy`), only for a KNOWN viewer, because the note renders only then (review of households H5 task F.6). The page decides when to show it: `!isLoading && !canEditCatalog` from `usePermissions()`. **Not `!canEditCatalog` alone**: while the role loads `canEditCatalog` is `false` for every role, so the note would flash for an owner, and a test that waits for the note would then prove nothing. Shown above the four catalog lists (non-empty), and with `settings.catalogReadOnlyItem` ("Only a household owner or manager can change this.") on the four catalog Info pages and the item Info tab. A member's empty catalog list uses the same text as its empty-state description.

**`NoLocationsEmptyState`** (`src/components/location/NoLocationsEmptyState/`) — what Pantry, Shopping, a cart and Cooking show in cloud mode when the person has no location (households H5 task F.7): "You have no locations in this household yet." (`noLocations.title`) and a **Create a location** button (`noLocations.create`). One prop, `onCreate`. Presentational, with a story and a smoke test. **`NoLocationsGate`** (`src/components/location/NoLocationsGate/`) decides when to show it and owns the Add Location dialog: it wraps the four route components, and the item page's Stock and log tabs (since the review of F.7), and renders its children unless the cloud location list has LOADED and is EMPTY. It has no story: it reads `useDataMode`, `useLocations` and `useCreateLocation`, and a story cannot `vi.mock`, so it is tested through the routes in `routes/noLocations.cloud.test.tsx`.

**`NoHouseholdScreen`** (`src/components/household/NoHouseholdScreen/`) — what a cloud page shows to a person in NO household (households H5b task G.8): an `h1` "You are not in any household." (`noHousehold.title`, focused when it appears) and three actions (owner decision O19). **Create a household** (the main, filled button) opens a dialog with an optional name (`noHousehold.nameLabel`, max 100); it uses `useCreateHousehold`, then `switchToHousehold(id, { to: '/' })`. **Switch to offline mode** (`neutral-outline`, with the hint `noHousehold.useLocalModeHint` as its description) sets `DATA_MODE_STORAGE_KEY` to `local` and reloads; the Clerk session stays. **Sign in to another account** (`neutral-ghost`, so three stacked buttons on a phone do not look equally important) runs `clearCache()` and then Clerk's `signOut()`, disabled while it runs; it is rendered only when `VITE_E2E_TEST_USER_ID` is unset, because `useClerk()` throws without a `ClerkProvider`. Stories `Default` and `CreateDialogOpen` mount the real screen; Storybook's Clerk stub (`.storybook/mocks/clerk.tsx`) makes `Default` show all three. **`NoHouseholdGate`** (`src/components/household/NoHouseholdGate/`) decides when to show it; see `routes/CLAUDE.md`, *No household*. It has no story, for the same kind of reason as `NoLocationsGate`.

**`OwnershipOfferBanner`** (`src/components/household/OwnershipOfferBanner/`, households H6b task K.6) — asks the person to become the owner of a household. No props. Mounted in `__root.tsx` in cloud mode, beside `OfflineBanner` and outside `NoHouseholdGate`; it renders nothing in local mode and nothing when there is no open offer. It reads `useMyOwnershipOffers()` and shows every offer with `dismissedAt: null`, from EVERY household the person is in (an offer may be for their other household, so the text names it). A `<section>` named "Ownership offers" (`ownership.banner.label`), one row per offer:

| Offer | Text | Buttons |
|---|---|---|
| `handover` | `ownership.banner.handover` | **Accept**, **Not now** (`dismissOwnershipOffer`; the offer stays open for the Members page) |
| `transfer` | `ownership.banner.transfer` | **Accept**, **Decline** |

Each button has `aria-describedby` pointing at its offer's text, so with two offers a screen reader says which household each **Accept** is for; the accessible name stays the visible word (review of K.6). While an answer is sent, the row's buttons are off. Accept worked: a notice `ownership.accepted` with the household name from the server's answer. The offer is gone (`isOfferGoneError`, or `false` from decline or Not now): a notice `ownership.gone`, for all three buttons. A notice is an `<output>` that takes the focus (the pressed button is gone by then) and has a **Close** button. Any other error: `ownership.failed` in a `role="alert"` under the row, and the offer stays. An `OfflineWriteError` shows nothing here (`offlineWriteLink` already showed a toast). The notices live in the banner, not in the row, because the hooks read the offer list again before they resolve, so the row is gone by then. **When the last offer goes, the `<section>` unmounts and mounts again with the notice**, so a test must look the region up again after an answer. Not now sends no live event, so the person's other tabs keep the banner until their next read. **Any test file with its OWN `vi.mock('@/generated/graphql', …)` factory that renders `__root.tsx` in cloud mode must stub `useMyOwnershipOffersQuery` and the accept, decline and dismiss mutation hooks**: `src/test/setup.ts` stubs them, but a per-file factory replaces it. Only the query stub is reached today: the stubs return no offer, so no row mounts and the three mutation stubs are called by no test (measured in the K.6 review by making them throw). Four files do today (`cooking.cloud.test.tsx`, `items/$id/stock.test.tsx`, `settings/household/locations/index.cloud.test.tsx`, `shopping/index.cloud.test.tsx`). A test that renders the banner with `MockedProvider` needs a `<Suspense>` inside it (the same unexplained empty render as `HouseholdNameCard.apollo.test.tsx`). Stories `Handover`, `Transfer`, `TwoOffers`, `AcceptFails`; the smoke test uses `.run()`, because only `.run()` calls the meta's `beforeEach` that sets cloud mode.

**`HouseholdSwitcher`** (`src/components/household/HouseholdSwitcher/`, households H7 task L.4) — **Switch to…**, item 9 of the household sidebar and of the mobile `/settings` accordion. One prop, `variant?: 'sidebar' | 'card'` (default `sidebar`, styled like the sidebar's links; `card` looks like `SettingsNavCard`, built from spans because a `<div>` is not valid inside a `<button>`). Renders nothing in local mode. Cloud: a `DropdownMenu` named by its trigger, like `LocationSwitcher`'s: one `menuitemradio` row per household from `useMyHouseholds()` (name as stored, no `capitalize`, a long name wraps, then the household role from `roles.household.*`), `aria-checked="true"` and a check on `isActive`, then a separator and **Create new**. One household is still a list. Choosing the current one only closes the menu. Choosing another calls `useSwitchHousehold().switchTo(id)`, which loads the same settings page again in the new household (since 2026-11-23; `/` before; see `useMyHouseholds` in `hooks/CLAUDE.md`), and keeps the menu OPEN (`preventDefault` in `onSelect`): every row is disabled and the chosen one spins until the page loads; a failure turns them on again and shows `householdSwitcher.switchError` as a toast (nothing more for an `OfflineWriteError`). A loading row and an error row stand in for the list. **Create new opens the dialog in the menu's `onCloseAutoFocus`, not in `onSelect`**: opened in `onSelect`, the menu's focus trap was still active and focus ended on a Radix focus guard instead of the name field. The dialog then puts focus back on the trigger when it closes. Stories `OneHousehold`, `TwoHouseholds`, `LongName`, `Loading`, `LoadError`, `Switching`, `CreateDialogOpen`, `Card`; the smoke test uses `.run()` (the meta's `beforeEach` sets cloud mode). `src/test/setup.ts` stubs `useMyHouseholdsQuery`, `useSetActiveHouseholdMutation` and `useCreateHouseholdMutation`, because every cloud test of the sidebar or the accordion reaches them; a file with its own `@/generated/graphql` factory must stub them too, or give a real Apollo client.

**`CreateHouseholdDialog`** (`src/components/household/CreateHouseholdDialog/`, households H7 task L.4) — `{ open, onOpenChange, onCloseAutoFocus? }`. **Known gap (found in task L.6, not fixed; the owner did not ask for a fix):** every `BAD_USER_INPUT` is shown as the name rule, so an `ALREADY_IN_HOUSEHOLD` refusal would show "Enter a name of 1 to 100 characters." No current server path sends that refusal to this dialog: it always sends `alsoWhenMember: true`, which skips the membership count. An optional name (max 100) and **Create**, which calls `useCreateAnotherHousehold().createAndSwitch(name.trim())`; the hook sends `""` as `null` (the server's default name) and `alsoWhenMember: true`, then moves the device into the new household. While it runs, Create spins, Create and Cancel are off and the dialog will not close; after a success they stay off until the page loads. Errors show in an `<output>` in the dialog: `BAD_USER_INPUT` gives the name rule (`settings.household.name.invalidError`) and focus goes back to the field; any other error gives `createHouseholdDialog.error`; an `OfflineWriteError` adds nothing. **The no-household screen keeps its own dialog** (`NoHouseholdScreen.tsx`), which uses `useCreateHousehold` and sends no `alsoWhenMember`, so two tabs there cannot make two households (H7 decision T70). Stories `Open`, `Creating`, `ServerError`.

**The Members page components** (`src/components/household/`, households H5b task G.9). All three take their data as props; the page (`routes/settings/household/members.tsx`) reads the hooks. Names render as stored, never `capitalize`.

- **`MemberList`** — one row per person: name, "(you)" on the caller's row, and the household role. `memberActions(callerRole, person)` (exported) decides the buttons: the owner gets the role control (a `Select`, `member` / `manager`) and Remove on every row but the owner's; a manager gets Remove on `member` rows only; a manager or member gets **Leave household** on their own row. Nothing while `callerRole` is `undefined` (the role is loading). Remove and Leave confirm through `DeleteButton`. While a leave runs (`leaving`) the caller's Leave is replaced by "Leaving…", and while a removal runs (`removingUserIds`) that row's Remove by "Removing…", both in an `<output>`: the confirm closes at once, and a second confirm would send a second request (review of G.9). **`onRemove` and `onLeave` catch their own errors**: the page shows its own text (`settings.household.members.error`) and resolves. If one rejected, `DeleteButton` would add its general `common.deleteFailed` toast, which says less (see `DeleteButton` above). **"No location roles" (households H5c task H.6, owner decision O28-A):** with `showLocationRoleMarks` on, a row whose `hasLocationRole` is `false` shows `settings.household.members.noLocationRoles` and a link, `settings.household.members.giveLocationRole`, to `/settings/household/locations`. `true` or `undefined` shows nothing. The Members page passes `usePermissions().canManageMembers`, so only an owner or manager sees it. With it on, the list renders a TanStack `<Link>` and needs the router in context. **Transfer ownership (households H6b task K.7):** `memberActions` also returns `canTransfer`, true for an owner on every row but their own. The button shows only when the page passes `onTransfer` (the page passes it for `usePermissions().canTransferOwnership`) and no offer is pending. Its accessible name is `transferLabel` ("Transfer ownership to {name}"), which holds the visible word (WCAG 2.5.3). It asks first in an `AlertDialog` titled `transfer`, with `transferConfirm`; this is not a `DeleteButton`, because nothing is deleted. With `pendingTransfer` set, that person's row shows `waiting` ("Waiting for {name} to accept") and a Cancel button named `cancelOfferLabel`, and no row shows Transfer: one offer at a time. When the person is not in the list, the same line shows in an extra row under it, so the owner can still take the offer back. `transferBusy` turns Transfer and Cancel off while a write runs. `onTransfer` and `onCancelTransfer` must not reject. The owner's own row says `ownerCannotLeave` ("The owner cannot leave. Transfer ownership first."). With `lastPerson`, the Leave confirm says `lastLeaveWarning` instead of `leaveConfirm` (owner decision O37-A). With `leaveDisabled` (households H6b task K.7b, owner decision O48), Leave shows but cannot be pressed: the page sets it until the server has answered the member list, because a list from the restored cache may be stale and give a wrong `lastPerson`.
- **`InviteDialog`** — mount it only while open. Step 1: the household role (`member`, plus `manager` when `canInviteManager`), then every location with a role picker on **No access** (`settings.locations.noAccess`). Rows on No access are not sent. Step 2: the link `${origin}/join/${token}` (`inviteLink`, `components/household/inviteLink.ts`) in a read-only field, **Copy link**, and the `linkNote` with the date. Copy uses `copyText` (`lib/copyText.ts`: the Clipboard API, then a hidden text area and `execCommand('copy')`). The fallback copies from that visible field (`copyText(text, { from })`), because the dialog's focus trap keeps a text area on the page body from getting focus. When both fail, the field's text is selected and an `<output>` says to copy it by hand. `locationsError` shows `locationsLoadError` (Create stays off); an empty list shows `noLocations` (Create stays on: O14-A).
- **`InviteList`** — the open invites: household role, location roles (or `noLocationRoles`), who made it, until when. **Copy link** on every row; **Revoke** for the owner on every row and for a manager on `member` invites only (O15-A). An empty list says `noInvites`. `onCopy` resolves to `false` when the link could not be copied; that row then shows the link in a read-only field, focused and selected. An empty role list cannot tell "made with none" from "its locations were deleted since"; the server sends the same thing for both.

- **`ActivityList`** (households H6 task J.6) — the household activity log, newest first. One `<li>` per row: one translated sentence and a `<time>` with the date and time (`formatDateTime`, `lib/formatDate.ts`). `activitySentence(entry, t)` (exported from the same folder) picks ONE key per action (`settings.household.activity.*`, the O39-A texts) and fills `{{actor}}`, `{{target}}`, `{{location}}`, `{{role}}` and `{{count}}` by i18next interpolation, never by joining parts, so `tw` keeps its own word order. **`LocationPager`** (`src/components/item/LocationPager/LocationPager.tsx`) — dot pager across locations for the item-detail Stock tab. Props: `locations: Location[]`, `currentIndex: number`, `activeLocationId: string`, `onChange(index)`, `panelId: string`, `tabIdPrefix: string`. A visually hidden `aria-live="polite"` region announces the location being viewed.

Two channels, neither of them colour (designer ruling, 2026-08-16 — every dot the same size and the same colour, fill marks the page you are on):
- **Fill = the page being viewed.** Every dot is `size-3` with `border-2 border-foreground-muted`; the viewed one adds `bg-foreground-muted` and the rest are `bg-transparent` — solid vs hollow, the standard pager-dot idiom. Shape rather than hue, so it survives greyscale and low vision. `foreground-muted` measures 8.73:1 against `background-elevated` in light mode and 7.30:1 in dark, well clear of WCAG 1.4.11's 3:1 for non-text indicators; the hollow dot's stroke *is* that colour and its centre *is* the page, so the stroke inherits the ratio. Do not add a halo ring for a third state — the `ring-importance-primary-accessory` this replaced measured 2.44:1 against the page and 1.16:1 against the dot it wrapped, both failing.
- **Words = which location is globally active.** The dots do not mark it at all (fill is spent on page position), so the caption under the heading carries it on every page — "Current location" when standing on it, "Current location: `<name>`" while viewing another page. That caption is the **only** sighted cue for it. That dot also keeps "(current location)" in its accessible name, and the viewed tab keeps `aria-selected`. **Terminology:** user-facing copy says *current location* (designer ruling, 2026-08-16) and the i18n keys match (`locationPager.currentHint` / `.currentElsewhere` / `.pageCurrent`); the code keeps *active* for the app-wide `activeLocationId` prop and `useActiveLocation`. Do not "fix" one to match the other.

`data-viewed` mirrors the styled state onto the DOM so tests can bind the fill to the right dot; the CSS itself is judged by eye in `LocationPager.stories.tsx` (both themes). Props: `value`, `onStep(next)`, `step`, optional `round(n)` (a normalizer applied to the stepped value before it clamps at 0 — omit for a plain ±1 stepper; both callers pass `(n) => roundToStep(n, step)` where rounding applies), `decreaseLabel`/`increaseLabel` (the buttons' `aria-label`s), `disabled?`, `readOnly?` (since households H5 task F.6: both buttons disabled, the input `readOnly` but not disabled, so the number can still be selected), optional `size?: 'sm' | 'default'` (default `'sm'`), and `inputProps` (spread onto the `Input` **last**, so the caller owns `value`/`onChange`/`onBlur`/`aria-label`/`id`/`step`/`className`). The component owns only the stepping arithmetic: `−` disables at `value === 0` (combined with `disabled`), and every stepped value clamps through `Math.max(0, …)` before reaching `onStep` — it holds no state of its own.

**`size` pairs the buttons' Button `size` with the input's default height**, so the group reads as one joined control rather than a taller input protruding past shorter flanking buttons. `'sm'` (the default, unchanged by adding this prop — `QuickUpdateDialog` never passes `size`) gives `icon-sm` buttons (`h-7`) over an `h-7 rounded-none text-right` input default. `'default'` gives `icon` buttons (`h-8`) over an `h-8 rounded-none text-right` input default; `ItemForm` passes `size="default"` on all four Stock-tab steppers and, critically, must **not** also spread a `className: undefined` key into `inputProps` — that key exists in the spread object even when its value is `undefined`, so it overrides the component's default and produces an unstyled `h-8` browser-default input wedged between the buttons (the Important-2 defect from the 2026-08-27 review: `ItemForm` originally nulled `className` this way, dropping `rounded-none text-right` and leaving a 32px input flanked by 28px buttons). Let the component's own default apply; override `className` only when the caller actually has a different class to give it.

**Both of its buttons are `type="button"`, and this is load-bearing, not cosmetic.** `QuickUpdateDialog` renders `QuantityStepper` outside any `<form>`, where a bare `<button>` is harmless — but `ItemForm` renders it inside its `<form onSubmit>`, and an untyped button there defaults to `type="submit"`: clicking `+`/`−` fired the form's native submit event and saved-and-navigated-away one click after the field first went dirty. Found via the E2E round-trip test in `e2e/tests/item-stock-input.spec.ts` (Task 4), not by any unit/story test — jsdom's `userEvent.click` reproduces the same native submit dispatch, but no existing test asserted `onSubmit` was *not* called from a stepper click.

**`ItemProgressBar`** (`src/components/item/ItemProgressBar/ItemProgressBar.tsx`) — the stock bar behind `ItemCard`, `StockProgressRow` and `GroupCard`. It draws a **segmented** bar (one segment per package) when the package target is 30 or less, and a **continuous** bar otherwise, or when a measurement item has no `amountPerPackage`. For a measurement item with `amountPerPackage`, the segmented bar divides `target`, `current`, `packed` and `unpacked` by `amountPerPackage`. The package target is rounded to 6 decimal places first, because in JavaScript `0.6 / 0.1` is `5.999999999999999`.

**`refillThreshold?: number`** draws a thin tick on the bar at the refill threshold (added 2026-09-23 — see `docs/features/items/2026-09-23-refill-threshold-marker-design.md`).

- **Unit:** the same unit as `target`. The component converts it to packages on a segmented bar, the same way it converts `target`.
- **Threshold `0` draws a tick at the left end** (user request, 2026-09-23). `getRefillMarkerLeft` returns `0%`, and the tick uses `translate-x-0`, so it stays inside the bar. At `0`, `getStockStatus` never warns, so this tick marks "no refill point".
- **No tick** when the prop is missing, when it is negative, when `target` is `0` (inactive item, or not stocked at the active location: `ZERO_STOCK` gives target `0` and threshold `0`), or when a segmented bar has 0 segments.
- **Clamps at the end:** a threshold at or above the target puts the tick at the right edge. There the tick uses `-translate-x-full`, so it stays inside the bar. Everywhere else, except at `0`, it uses `-translate-x-1/2` (centred on the point).
- **Segmented bar:** it draws `floor(packageTarget)` segments (for example target 2000 with 300 per package is 6.67 packages, so 6 segments). The tick clamps to the end of the last drawn segment. A whole-number threshold sits in the gap after that segment. A fractional one sits inside a segment. The scaled threshold is rounded to 6 decimal places before the whole-number check, because `0.3 / 0.1` is `2.9999999999999996`.
- **Test hooks:** the tick is `data-testid="refill-marker"`, `aria-hidden="true"`. Its `data-threshold` is the clamped threshold **in packages on a segmented bar** and **in item units on a continuous bar**. The exported `getRefillMarkerLeft({ threshold, target, segmented })` returns the CSS `left` value.
- **Screen readers:** a `sr-only` span reads `common.refillWhenBelow` ("Refill when below N") with the **unscaled** value the user typed, for example "Refill when below 750", not "Refill when below 1.5". It has no unit, because the bar does not know the unit name.

**`StockProgressRow`** (`src/components/item/StockProgressRow/StockProgressRow.tsx`) — the Clear · `x / y` label · `ItemProgressBar` · Fill-to-Full row shared by `QuickUpdateDialog` and `ItemForm`'s Stock tab: `grid grid-cols-[auto_1fr_auto]`, a `space-y-1` middle column (the `flex gap-1 items-baseline text-xs text-right text-foreground-muted` label line with a leading spacer and a single span reading `` `${quantityLabel} ${unitLabel}` ``) over the bar. Purely presentational — it takes every display value as a prop (`quantityLabel`, `unitLabel`, `current`, `target`, `status`, `targetUnit`, `packed`, `unpacked`, optional `measurementUnit`/`amountPerPackage`/`refillThreshold`, optional `size`, `onClear`/`onFill`, `clearDisabled`/`fillDisabled`, `clearLabel`/`fillLabel`) and computes nothing itself — both callers derive them from the shared `getStockPreview` (`lib/quantityUtils.ts`). Its two action buttons are `type="button"` for the same reason `QuantityStepper`'s are.

Both callers pass the **live** value — `QuickUpdateDialog` its `localRefill` state and `ItemForm`'s Stock tab its `refillThreshold` form state — so the tick moves while the user edits Refill, before saving.

**`size?: 'sm' | 'default'` (default `'sm'`) pairs the Clear/Fill arrows with the `QuantityStepper` `size` on the same surface.** Same two values and the same mapping as `QuantityStepper`: `'sm'` → Button `size="icon-sm"` (`h-7 w-7`), `'default'` → Button `size="icon"` (`h-8 w-8`). **`QuickUpdateDialog`** (`src/components/item/QuickUpdateDialog/index.ts`) — pantry-page dialog for bulk-editing a single item's stock in one submit. Triggered by the calculator icon button on each `ItemCard` in pantry mode. Composes `QuantityStepper` (all four quantity fields) and `StockProgressRow` (the Clear/bar/Fill row), plus Pack/Unpack buttons (mirrors item info tab logic via `computePack`/`computeUnpack`). Submits a single mutation with `{ packedQuantity, unpackedQuantity, targetQuantity, refillThreshold }` plus a conditional `dueDate`. Pack/Unpack/Fill-to-Full logic lives in pure functions in `quantityUtils.ts` (`computePack`, `computeUnpack`, `computeFillToFull`); the progress row's display derivation (`current`, the display-packed value, `unitLabel`/`quantityLabel`, `status`, `isAtZero`/`isAtFull`) is the same `getStockPreview` that `ItemForm`'s Stock tab calls, so the two surfaces cannot drift on how a preview reads.

**A failed save shows an inline message** (since 2026-11-19, `docs/global/bugs/2026-11-19-bug-screens-ignore-save-errors.md`). When `onSubmit` rejects, the dialog stays open with the numbers kept and shows `common.saveFailed` in a `role="alert"` line, the same way `ShelfFilterPicksDialog` and `NewItemDialog` do. The next press clears it. So a caller's `onSubmit` must let the error reach the dialog (all four pantry views do, with `try`/`finally`). Before, the dialog caught the error and showed nothing.

**"Expires on" (designer ruling, 2026-08-27, reversing the 2026-05-31 "quick-update never touches `dueDate`" decision — see `docs/features/pantry/2026-05-31-brainstorming-quick-update-dialog.md`'s dated addendum).** The date field renders as the **third row of the same `grid-cols-[auto_auto_auto]` grid** as Packed/Unpacked above it and Target/Refill below it (label · `Input type="date"` · hint, lined up with the other rows' columns), directly under Unpacked and above the progress bar, but only when `item.expirationMode === 'date'` — that global mode is Info-tab configuration, read here and never written; the due date itself is per-location `ItemStock` state, exactly like `ItemForm`'s Stock tab (which gates and formats it identically and, since 2026-09-22, puts it in the same position — third, after Unpacked and above the progress row; the only difference is structural, since the Stock tab is a `space-y-2` stack of blocks rather than a grid, so its copy is a plain `<div>` and joins no grid — see `routes/items/CLAUDE.md`). The conditional three-cell group is a **fragment**, not a wrapping element — inside a grid a wrapper collapses to one grid item and breaks the column alignment the row exists to achieve. `localDueDate` is seeded from `item.dueDate` (converted to the `YYYY-MM-DD` string `<input type="date">` needs, same conversion as `itemToFormValues` in `routes/items/$id/stock.tsx`) in the same reset effect as the four quantity locals, and `isUntouched` compares it alongside them so Update stays disabled until something actually changed.

**The submitted `dueDate` key is OMITTED entirely — not sent as `undefined` — whenever the field isn't rendered.** `toUpdateItemInput()` (cloud) and `writeItemUpdate()`/`upsertItemStock()` (local, `db/operations.ts`) both read a field's *absence* from `updates` as "leave it alone" and its *presence* (even as `undefined`) as "clear it". An item in `'days from purchase'` or `'disabled'` mode never renders the field, so its `onSubmit` payload must carry no `dueDate` key at all — a conditional spread (`...(item.expirationMode === 'date' ? { dueDate: … } : {})`) achieves this; unconditionally including the key would silently wipe that location's stored due date on every Update press for such an item. When the field IS rendered and the user clears it, the key IS still included as `undefined`, which both `toUpdateItemInput` and `upsertItemStock`'s `{...existing, ...fields}` spread correctly read as "clear the stored value" — clearing is the intended outcome there, unlike the omitted-key case. All four pantry views (`PantryListView`, `ShelfDetailView`, `VendorDetailView`, `RecipeDetailView`) forward the dialog's `onSubmit` object as-is into `updateItem.mutateAsync({ id, updates })` rather than re-destructuring named fields, so the conditional presence survives the forward untouched; each casts to `Partial<StockFields>` because the dialog's `dueDate?: Date | undefined` is stricter than `StockFields`' `dueDate?: Date` under `exactOptionalPropertyTypes` — the same cast `routes/items/$id/stock.tsx` already uses for its own `ItemUpdatePayload`. **This is a shared convention, not a dialog-local one:** `buildStockUpdates` in `routes/items/$id/stock.tsx` emitted the key unconditionally until 2026-08-29 and silently wiped a location's stored date on every Stock-tab quantity save for an item not in `'date'` mode — issue #261, `docs/features/items/2026-08-29-bug-stock-tab-clears-duedate.md`. Any surface that renders this field behind a mode gate must gate the payload key behind the same condition.

**Row order (designer ruling, 2026-09-22) — a SHARED convention across both stock surfaces, not a dialog-local one.** Top to bottom: **Packed → Unpacked → Expires on (date mode only) → progress bar → Target → Refill below**. The item detail **Stock tab** (`ItemForm`'s `sections={['stock']}` block, see `components/item/ItemForm` below) uses the same order, with its own labels "Target Quantity" / "Refill When Below". Change one surface and you must change the other.

Packed and Unpacked are the fields edited most often, so they lead. "Expires on" follows them because it is per-location state the user updates when buying something, not configuration of the bar. Target and Refill below *configure* the progress bar — `getStockPreview` passes `targetQuantity` through as the bar's `target` (`ItemProgressBar`'s denominator) and derives the colour from `refillThreshold` via `getStockStatus` (amber exactly **at** a non-zero threshold, red **below** it) — so they follow it. This reversed the original order (progress bar → Target → Refill below → Packed → Unpacked → Expires on). Reasoning and the reversed decision: `docs/features/pantry/2026-08-27-brainstorming-quick-update-stock-settings.md`, addendum 2026-09-22.

Each surface pins the order with **two** tests — a date-mode fixture covering all six rows and a non-date-mode fixture covering the five that remain when "Expires on" is absent (`QuickUpdateDialog.test.tsx`, `ItemForm.test.tsx`). Both use the shared `expectDocumentOrder` helper in `src/test/utils.tsx`, whose failure message names the two rows that are out of order.

**Stock settings rows.** Editable **Target** and **Refill below** steppers — the same per-location `ItemStock` fields the item form owns as "Target Quantity" / "Refill When Below", shortened here so the label column stays narrow. They are the last two rows of the **same** `grid-cols-[auto_auto_auto]` grid as Packed/Unpacked — not a second grid of their own: two adjacent grids size their columns independently, so their steppers would not line up. In the merged grid the third column carries the Unpack/Pack buttons on the first two rows, the "Expires on" hint on the third (when the item is in `expirationMode === 'date'`), and the muted hints (`Inactive when 0`, `Warns on low stock`) on the last two.

**`StockProgressRow` is inside that grid too**, wrapped in a `col-span-3 my-2` cell rather than sitting outside as a sibling of it. A row outside the grid would let the label column and the stepper column drift between the rows above the bar and the rows below it. `my-2` restores the 16px this row had as a `space-y-4` sibling: `gap-2` gives 8px and the margin adds the other 8px, since grid-item margins add to the gap instead of collapsing. Document order, the shared grid, and the `col-span-3` cell are all pinned by tests in `QuickUpdateDialog.test.tsx` — including a non-date-mode fixture, so the order still holds when the "Expires on" row is absent. Both settings are labelled and stored in the item's **tracking** unit (the unpacked row's unit), not the package unit. Target steps by 1 in `package` mode and by `consumeAmount` otherwise (mirroring `ItemForm`'s `step={targetUnit === 'package' ? 1 : quantityStep}`); Refill below always steps by `consumeAmount`. Both clamp at 0.

**Everything in the preview reads the local values, never `item.*`** — the progress status, the bar's `target`, the `x / y` label and Fill to Full's destination all follow what has been typed but not yet saved, so raising the threshold shows the low-stock colour *before* Update is pressed. `isUntouched` covers all four values, so Update stays disabled until something actually changed.

**Step size falls back to 1.** The unpacked stepper's `step` is `item.consumeAmount > 0 ? item.consumeAmount : 1` — a `> 0` guard, never `?? 1`, which does not fire for a stored `0` and left `step` at 0: both `+` and `−` became no-ops and the input rendered the invalid `step="0"`. Same form as `cooking.tsx` and the recipe items tab. This is deliberately the **opposite** of `ItemForm`'s `quantityStep` (`consumeAmount > 0 ? consumeAmount : 'any'`, which rounds nothing and leaves the unset consume amount visible as unconfigured) — do not unify them: a `+`/`−` increment must be non-zero to be usable at all, whereas a free-text number field can simply accept what the user typed.

**`ItemSearchTail`** (`src/components/item/ItemSearchTail/ItemSearchTail.tsx`) — the two tail sections beneath a location-scoped item list while searching: "N not in this list" (stocked in the active location, absent from this page's list) then "N not stocked here" (exists globally, no `ItemStock` here). ## Unit Display Components

**Units on cards and progress rows are plain trailing words, not a component.** There is no `UnitBadge` — it was deleted on 2026-08-29 (issue #257). The bordered pill's `opacity-75` composited `text-foreground-muted` down to 4.44:1 on `background-elevated` and failed WCAG AA on **every** light surface, and the token itself was innocent (8.68:1 opaque), so darkening it would have restyled the ~70 files that share it. Each of the three render sites now folds the unit into the quantity's own already-muted `text-xs text-foreground-muted` element as a trailing bare word — no parentheses, no border, full opacity. All three space the `/` (`3 / 4`, never `3/4`):

| Site | Renders |
| --- | --- |
| `ItemCard` | `3 / 4 pack` · `3 (+2) / 4 pack` · `750 / 1000 ml` |
| `GroupCard` | `12 / 20 pack` — the explicit `DEFAULT_PACKAGE_UNIT` from `@/types`, since group totals are genuinely pack-counted |
| `StockProgressRow` | `3 / 4 pack` (its `quantityLabel` comes from `getStockPreview`, which has always spaced the `/`) |

Because the unit shares one text node with the numbers, tests must query them together — `getByText('1 / 3 bunch')`, never `getByText('bunch')`. See `docs/global/bugs/2026-08-29-bug-unit-badge-contrast.md`.

**`UnitInline`** (`src/components/shared/UnitInline/`) — inline `(unit)` text for form labels. Props: `unit?: string | undefined`, `placeholder?: string` (default `"pack"`). Renders `(unit ?? placeholder)` with parentheses included. Pass `placeholder="?"` for measurement-unit labels where the unit may be unset — the `?` signals an unresolved setting to the user. Used in ItemForm.

## Dialog Layout Pattern

shadcn/ui `Dialog` uses a three-zone layout: `DialogHeader` → `DialogMain` → `DialogFooter`.

**`DialogMain`** (`src/components/ui/dialog.tsx`) — content wrapper between header and footer. Applies `mx-4 my-3`. Use for the main body of any dialog (forms, descriptions, lists).

**`DialogHeader`** — redesigned as a horizontal bar with an inline close button. Renders `flex items-center border-b border-accessory-default px-4 py-3`. The close button (`X` icon) is appended automatically via a flex spacer — do not add a separate close button.

**`DialogFooter`** — has `m-4` for consistent edge spacing.

## InfoForm Pattern

Entity form components (`TagInfoForm`, `RecipeInfoForm`, `VendorInfoForm`, `TagTypeInfoForm`) own their local state and expose a flat callback API:

- **Props**: `entity?` (initial values), `onSave(data)` (called with trimmed values on submit), `isPending?`, `onDirtyChange?(isDirty)`, plus entity-specific options (e.g. `typeReadonly?` on TagInfoForm)
- **State**: all field values are internal; parent never needs to track them
- **Dirty**: edit mode compares current values to initial; create mode is dirty as soon as any field is filled
- **Validation**: inline error messages (not toast), submit/Enter blocked when invalid
- **A failed save** (since 2026-11-19, `docs/global/bugs/2026-11-19-bug-screens-ignore-save-errors.md`): the route catches it and shows a toast with `showSaveError` (`lib/saveError.ts`). `TagInfoForm` and `RecipeInfoForm` mark the edit as saved when Save is pressed, before the save ends, so their `onSave` may return a promise: when it rejects, the form puts the old baseline back, so the edit is unsaved again and Save is enabled. The form swallows that rejection, so the route rethrows after its toast. `VendorInfoForm` compares with the `vendor` prop instead, so its route only shows the toast and does not rethrow
- **`ItemForm`** (`components/item/ItemForm`) does not await `onSubmit`, and its `onSubmit` must not reject. Both callers (`routes/items/$id/index.tsx`, `routes/items/$id/stock.tsx`) catch a failed save and show `showSaveError`; they do not bump `savedAt`, so the form stays dirty
