# Custom Hooks

## Cloud read fetch policy

**Every cloud READ query in this app runs on `fetchPolicy: 'cache-and-network'`, with one named exception.**

Apollo's default is `cache-first`. That is wrong here because the cloud Apollo cache is
persisted to IndexedDB (`Player1InventoryCloudCache`) and restored **before React mounts**
(`main.tsx` → `bootstrap.ts` → `apollo/persistence.ts`). The snapshot has no TTL and no
schema version, so `cache-first` finds a complete answer in it and **sends no request at
all**. The data stays at whatever this device last saw. On an iOS home-screen PWA there is
no reload button and no pull-to-refresh, so nothing else asks either. Fixed 2026-09-22 —
see `docs/global/bugs/2026-09-22-bug-cloud-queries-cache-first.md`.

**The policy always comes in a pair.** With `cache-and-network` the network leg runs on
every mount and **fails offline**, so every cloud branch reports
`isError: !!cloud.error && !cloud.data` — never bare `!!cloud.error`. A failed refetch over
a good cache is not an error state; reporting one would put an error screen in front of
data the user can read, which is exactly what the offline work exists to prevent.

**The pair has a second half: `isLoading` must mean "nothing to show yet", not "a request
is in flight".** With `cache-and-network` Apollo hands back the restored snapshot AND keeps
`loading: true` until the network answers. Ten components return a spinner straight out of
`if (isLoading)` (`PantryListView.tsx:239`, `ShelfGroupView.tsx:151`,
`routes/items/$id.tsx:90` and seven more), so passing Apollo's `loading` through hid
readable data behind a spinner on every cloud mount. Every cloud branch now reports
`isLoading: cloud.loading && !cloud.data` — 24 sites across nine hook files. Use
`isFetching` when you want "a request is in flight"; `useItems` and `useStockedItems`
expose it (`cloud.networkStatus < 7`) and no component reads it yet.

**Never add `errorPolicy: 'all'`.** Measured on Apollo Client 4.1.6: the default `'none'`
leaves the cached result in `data` after a failed network leg, while `'all'` moves it to
`previousData` and leaves `data` **undefined** — it blanks the screen for an offline user.
It is pinned RED by tests in `useLocations.test.tsx` and `cloudFetchPolicy.cloud.test.tsx`.

**One query stays on `cache-first`, on purpose:**

| Query | Why |
|---|---|
| `useCloudLocationKnown` (`GetLocations`) | Observes the same document and variables as `useLocations`, so it rides that hook's cache write for free. |

There used to be a second one. `useLastPurchaseDate` ran once per `ItemCard` with
`itemIds: [one]`, and `lastPurchaseDates` is keyed by `['itemIds','locationId']`
(`apollo/cloudCache.ts`), so every card owned a separate cache entry that deduplication
could not merge — `cache-and-network` there would have sent one request **per visible
card**. It was pinned to `cache-first` and left knowingly stale instead. **Deleted in
#305.** `ItemCard` now takes `lastPurchaseDate` as a required prop, fed from
`useItemSortData`'s batch query, so the batch is the only `LastPurchaseDates` query in the
app and every card's date refreshes with the list.

**Coming back to the app refetches every active query. There is no opt-out.**
`cache-and-network` refreshes a query when its component **mounts**, and resuming a
backgrounded PWA mounts nothing — so an app left open stayed as stale as the moment it was
last opened. `apollo/ApolloWrapper.tsx` handles this: its `visibilitychange` listener (which
already saved the cache on hide) calls `client.refetchQueries({ include: 'active' })`
when the app becomes visible. Three rules, all pinned by tests in `ApolloWrapper.test.tsx`:

| Rule | Why |
|---|---|
| Online only (`isOffline()` returns early) | Every request would fail. The hooks keep showing cached data either way, and the failures cost battery and mobile data. |
| At most once per `RESUME_REFETCH_MIN_GAP_MS` (30 s) | People switch apps constantly on mobile. Rows cannot meaningfully change in a shorter gap. |
| The gap clock starts at **mount**, not at 0 | Every query on screen already ran a network leg at mount, so a glance away and back a few seconds after launch must not fire a second round. |

**The opt-out that used to be here is gone (#305).** Two constants in
`apollo/constants.ts` let a query set a `context` marker that `onQueryUpdated` skipped.
They existed only because `useLastPurchaseDate` ran one `LastPurchaseDates` query per
`ItemCard`: a pantry of 40 items sent 40 requests on every resume. Measured with a counting `ApolloLink`, 20 cards produced 20 requests. `ItemCard`
now receives the date as a prop, so the only `LastPurchaseDates` query on screen is
`useItemSortData`'s single batch one and refetching everything costs one request.
`ApolloWrapper.test.tsx` (`ApolloWrapper resume refetch cost`) measures real requests
through a counting link and pins that the count does **not** grow with the number of
cards: 3 cards and 30 cards both send 1 request at mount and 1 more on resume.

It stamps no `setLastSyncedAt`: `save()` already stamps every 5 seconds while online, so a
stamp here would be replaced by a coarser one within five seconds. Local mode is untouched
— the effect returns early on `!userId`, so the listener is never attached.

This is also why the `isLoading` guard above is not optional. A refetch sets `loading` true
again while keeping `data`, so without the guard every resume would drop a spinner over the
pantry the user was reading. Pinned by `cloudFetchPolicy.cloud.test.tsx` → `a resume
refetch does not put a spinner over the pantry`.

**Two hooks reading one document still cost one request.** `useItems`/`useStockedItems`
(`PantryData`), `useItem`/`useItemStocks` (`ItemStocksForItem`) and
`useAllActiveCarts`/`useLastPurchasedByVendor` (`AllCarts`) each carry the policy on both
halves. Apollo's `queryDeduplication` (on by default, never disabled in
`apollo/client.ts`) collapses the identical in-flight operation. Measured in
`cloudFetchPolicy.cloud.test.tsx` → `two hooks on one document still cost one request`.
Giving the network leg to only one of a pair would work too, but then the pair breaks the
moment the other half mounts alone.

**The one cloud read outside `src/hooks/`** is `useAllCartItemsQuery` in
`routes/shopping/index.tsx`. Its policy is pinned by an options-capture test in
`routes/shopping/index.cloud.test.tsx` instead of the real-Apollo fixture the hooks get.

**Navigation:**
- `useAppNavigation()` (`src/hooks/useAppNavigation.ts`) - Tracks navigation history in sessionStorage, provides `goBack()` function for smart back navigation to previous app page (fallback to home). Uses `router.history.push(previousUrl)` to preserve full URL (including search params) when going back.
- `useNavigationTracker()` (`src/hooks/useNavigationTracker.ts`) - Global hook (used in `__root.tsx`) that records every page visit as a full URL (`pathname + searchStr`) in sessionStorage. When params change on the same page, updates the last entry in place rather than appending a new one.

**Item List State:**
- `useUrlSearchAndFilters()` (`src/hooks/useUrlSearchAndFilters.ts`) - Manages search query, tag filter state, vendor/recipe filter state, and UI visibility (filters panel, tags visible) via URL params (`?q=`, `?f_<typeId>=`, `?f_vendor=id1,id2`, `?f_recipe=id1,id2`, `?filters=1`, `?tags=1`). Uses `router.history.replace` to update params in place (same history entry). Note: `filterState` only contains tag type filters — `vendor` and `recipe` keys are reserved and excluded from `filterState`. Exposes `selectedVendorIds: string[]`, `selectedRecipeIds: string[]`, `toggleVendorId(id)`, `toggleRecipeId(id)`, `clearVendorIds()`, `clearRecipeIds()`.
- `useSortFilter(storageKey)` (`src/hooks/useSortFilter.ts`) - Manages sort field and direction via localStorage key `${storageKey}-sort-prefs`. Used by all item list pages for per-page sort persistence. Accepts optional `defaultSortBy` option (defaults to `'name'`).
- `useScrollRestoration(key, scrollRef)` (`src/hooks/useScrollRestoration.ts`) - Saves/restores the scroll position of a scroll container element for a given key (typically the full URL). The app shell pins `<main>` to the viewport so the window never scrolls — list views scroll inside an inner `overflow-y-auto` container, so the hook operates on `scrollRef.current.scrollTop` / `.scrollTo`, not `window`. Saves scroll on component unmount (SPA navigation away); restores after data loads. Usage: attach a `useRef<HTMLDivElement>(null)` to the scroll container, call with `currentUrl` from `useRouterState` + the ref, then call `restoreScroll()` in a `useEffect` conditioned on `!isLoading`. For the 4 detail-page Items tabs (tags/vendors/recipes/shelves) the scroll container is owned by `LayoutInnerPages` and shared via `<Outlet>`; those callers read the ref from `useInnerPageScrollRef()` (a context exposed by `LayoutInnerPages`).

**Data Utilities:**
- `useVendorItemCounts()` (`src/hooks/useVendorItemCounts.ts`) - Returns `Map<vendorId, number>` of item counts per vendor, memoized with useMemo for performance
- `useTagItemCounts()` (`src/hooks/useTagItemCounts.ts`) - Returns `Map<tagId, number>` of global item counts per tag, memoized off `useItems()` + `useTags()`. Every tag gets an entry, including zeros. **Counts expand descendants** (`getTagAndDescendantIds`, the same walk `lib/shelfUtils.ts` uses): the shelf tag filter selects a tag *and all its descendants*, so a direct-assignment count would report 0 for a parent tag that in fact selects a dozen items. An item carrying both a parent and its child counts **once**. Location-unaware by design — these are global item↔tag relations. Distinct from the per-id `useItemCountByTag` (one async query per id, direct assignments only), which cannot be called in a badge loop.
- `useRecipeItemCounts()` (`src/hooks/useRecipeItemCounts.ts`) - Returns `Map<recipeId, number>` of global item counts per recipe, memoized off `useItems()` + `useRecipes()`. Every recipe gets an entry, including zeros. Recipes have no hierarchy, so membership is plain (mirrors the recipe branch of `lib/shelfUtils.ts`); counting from the item side also drops recipe entries pointing at deleted items. Location-unaware by design. The map-shaped counterpart to the per-id `useItemCountByRecipe`.
  - All three map-shaped count hooks are consumed together by the shelf filters tab (`settings/shelves/$shelfId/filters.tsx`), where each tag/vendor/recipe badge renders `` ` (${count})` `` after the name.
- `useItemSortData(items)` (`src/hooks/useItemSortData.ts`) - Returns `{ quantities, expiryDates, purchaseDates }` for sort operations on item lists. `quantities` is a `useMemo` (synchronous, no race condition). Local mode: `expiryDates` and `purchaseDates` are TanStack Query queries under the `['sort', ...]` key namespace. Cloud mode: uses `useLastPurchaseDatesQuery` (Apollo batch query) with `locationId: activeLocationId` and derives expiry dates synchronously — no TanStack Query involved. `lastPurchaseDates(locationId:)` is `ID!` since PR 3a Task 4, so the cloud query is gated on `useCloudLocationKnown`. Used by all five item list pages, by `routes/cooking.tsx`, and by the four Settings assignment tabs. Checkout explicitly invalidates `['sort', 'purchaseDates']` after purchase (local mode) and evicts the `lastPurchaseDates` root field (cloud mode). **`purchaseDates` also feeds every `ItemCard`'s `lastPurchaseDate` prop since #305** — the card fetches nothing of its own, so this is the ONLY `LastPurchaseDates` query in the app. Search-tail rows in bucket 3 (not stocked here) are absent from the map, so they get `undefined`; that matches the old per-card query, and their expiry chip is hidden anyway because it also needs `currentQuantity > 0`.
- `useItemLogs(itemId)` (`src/hooks/useInventoryLogs.ts`) - Returns inventory log entries for an item **at the active location**. Dual-mode: local uses TanStack Query + Dexie (`getItemLogs(itemId, activeLocationId)`, with the location in the query key); cloud uses `useItemLogsQuery` with `variables: { itemId, locationId: activeLocationId }`. **`itemLogs(locationId:)` is `ID!` since PR 3a Task 4** — there is no server-side default-location fallback any more, so the cloud branch is gated on `useCloudLocationKnown` and stays `isLoading` until `GetLocations` confirms the active id is a real cloud `Location`. Two-location proof: `useInventoryLogs.cloud.test.tsx`.
- `useAddInventoryLog()` (`src/hooks/useInventoryLogs.ts`) - Mutation hook to add an inventory log entry. Dual-mode: local calls `addInventoryLog` with the active location's id threaded in (matches the read side, `useItemLogs`, which filters by `activeLocationId`); cloud calls `useAddInventoryLogMutation` with a `locationId` resolved **at call time** by `useCloudLocationId()`, never the render-time active id. `addInventoryLog(locationId:)` is `ID!` since PR 3a Task 4: a write sent with the `'local'` sentinel is refused with `FORBIDDEN` and lost, and unlike a read it does not self-correct. Pinned by the `a fresh cloud session, before GetLocations has resolved` block in `useInventoryLogs.cloud.test.tsx`, whose fixture removes the `active-location-id:cloud` slot. The cloud branch sends **no `refetchQueries`** — nothing to target, and refetching `ItemLogs` by NAME would refetch every observer carrying that name.
- `useConsumeRecipes()` (`src/hooks/useRecipes.ts`) - Batch mutation hook for cooking done. Sends all item quantity updates, inventory logs, and recipe `lastCookedAt` stamps in a single call. Dual-mode: local uses `consumeRecipesBatch` (Dexie transaction); cloud calls `useConsumeRecipesMutation` (Apollo). **`ConsumeRecipesInput.locationId` is `ID!` since PR 3b Task 4**, and the cloud branch resolves it **at call time** with `useCloudLocationId()` — the `'local'` sentinel of a fresh cloud session would lose the whole cook to `FORBIDDEN`. Used exclusively by the cooking page `handleConfirmDone`.

**Shopping:**
- `useVendorCartCounts()` (`src/hooks/useVendorCartCounts.ts`) - Returns `Map<vendorId, { count: number; inactiveCount: number }>` for the `/shopping` index cards + the `'count'` sort. `count` is items with this vendor stocked in the **active location**; `inactiveCount` is the subset with `targetQuantity === 0`. **No mode branch since PR 3b** — cloud used to keep a global tally and hard-code `inactiveCount: 0`, because a cloud `Cart` had no `locationId` and the count would not have matched the cart the card opened. PR 3a added the column and PR 3b re-keyed `Cart.id`, so both modes count the same way. Distinct from `useVendorItemCounts()` below, which stays global/location-unaware for `/settings/vendors` — vendor management is location-independent, so the two pages showing different counts for the same vendor is expected, not a bug (see `apps/web/src/routes/CLAUDE.md`).
- `useVendorCart(vendorId: string | null)` (`src/hooks/useShoppingCart.ts`) - Gets the active location's cart for a specific vendor (null = "No vendor" cart). Local: TanStack Query keyed `['cart', 'vendor', vendorId, { locationId }]`; `getCart` is a pure read — carts are bootstrapped up front by `ActiveLocationProvider` (see `useActiveLocation()` below), not created lazily here. Cloud: `vendorCart(vendorId, locationId)`, with `locationId` **`ID!` since PR 3b Task 4**. That query CREATES the cart when it is missing, so the server demands the `member` role on the location — the cloud branch is therefore gated on `useCloudLocationKnown` and stays skipped until `GetLocations` confirms the active id.
- `useAllActiveCarts()` (`src/hooks/useShoppingCart.ts`) - Returns the **active location's** carts (one per vendor plus the no-vendor cart). Local: TanStack Query keyed `['cart', 'all-active', { locationId }]`. Cloud: the whole-account `allCarts` query, narrowed client-side to the carts whose `parseCartId(id).locationId` is the active one — never by `id.startsWith(locationId + ':')`, because a location id is not a prefix-free code.
- `useLastPurchasedByVendor()` (`src/hooks/useShoppingCart.ts`) - Returns a `Map<string | null, Date | null>` of each vendor cart's `lastPurchasedAt` (the `null` key is the no-vendor cart). Drives the `'recent'` sort on the shopping index. **Dual-mode, and both branches now do the same thing.** Local: TanStack Query keyed `['cart', 'last-purchased-by-vendor', { locationId }]`, reading the active location's carts and keying by `parseCartId`'s `vendorId`. Cloud: derived from the **same `useAllCartsQuery`** `useAllActiveCarts()` runs, so Apollo serves it from cache (no extra round trip) and `useCheckout()`'s existing `AllCartsDocument` refetch keeps it fresh; it drops carts at other locations and keys by `parseCartId`'s `vendorId` too. **Cloud cart ids stopped being bare in PR 3b** — they are `${locationId}:${vendorId | 'no-vendor'}` like local ones, and the old comment saying `parseCartId` must not be used here was true before the re-key and false after it. Without the location filter one vendor's two carts would both write the same map key and the later one would win, so the page would sort by another location's purchase date.

**Cloud / Auth:**
- `usePostLoginMigration()` (`src/hooks/usePostLoginMigration.ts`) - Cloud mode only. Detects when a signed-in user has local IndexedDB items and has not been prompted before (localStorage `migration-prompted` key). Exposes `state: MigrationState`, `dismiss()`, and `importData(conflictResolution)`. `importData` calls `fetchLocalPayload()` then `importCloudData()` to migrate local data to cloud. Used by `PostLoginMigrationDialog`.

**Location:**
- `useLocations()` (`src/hooks/useLocations.ts`) - Returns all locations. **Dual-mode** (mirrors `useShelves`): local uses TanStack Query + Dexie; cloud uses `useGetLocationsQuery` (Apollo), deserialized through `deserializeLocation`. The cloud query runs on **`fetchPolicy: 'cache-and-network'`**, like every other cloud list hook. It was the only one left on Apollo's default `cache-first`, and because the cloud cache is persisted to IndexedDB and restored before React mounts (`apollo/persistence.ts`, no TTL, no schema version), a complete `ROOT_QUERY.locations` array in the restored snapshot satisfied `cache-first` outright — **no `GetLocations` request was sent at all**, so a location added on another device never appeared (fixed 2026-09-21). It sets **no `errorPolicy`** on purpose: measured on Apollo Client 4.1.6, the default `'none'` keeps the cached result in `data` when the network leg fails, while `errorPolicy: 'all'` moves it to `previousData` and leaves `data` undefined — which would empty the location switcher for an offline user. For the same reason the cloud branch reports `isError: !!cloud.error && !cloud.data`, so a failed refetch over a good cache is not an error state. `useCloudLocationKnown` deliberately stays on `cache-first` and rides this hook's cache write. Also exposes `useCreateLocation`, `useUpdateLocation`, `useDeleteLocation`, `useReorderLocations`, all dual-mode. Two places where the cloud contract diverges from the shelves pattern it otherwise copies:
  - **`updateLocation` cannot set `order`.** `UpdateLocationInput` is name-only (`apps/server/src/schema/location.graphql`), unlike `updateShelf`. The cloud branch throws `CLOUD_LOCATION_ORDER_NOT_UPDATABLE` on an `order` update rather than dropping it silently, which would look like a persisted reorder that never happened. Reordering goes through `useReorderLocations`.
  - **`reorderLocations` returns `[Location!]!`**, not `reorderShelves`' `Boolean`. The cloud branch therefore `cache.writeQuery`s the returned list into `GetLocations` instead of refetching — the reorder settles in one round trip. The other three cloud mutations use `refetchQueries: [{ query: GetLocationsDocument }]`, which is the cloud stand-in for the local `invalidateQueries(['locations'])`: a mutation result can update a normalized entity but never tells Apollo that the `Query.locations` root field gained or lost an entry. Delete's local branch invalidates five key families for the cascade; cloud refetches only `GetLocations`. **Cloud carts and inventory logs now cascade in the DATABASE** — `Cart.locationId` and `InventoryLog.locationId` both carry `onDelete: Cascade` since PR 3a — but the cloud mutation still refetches only `GetLocations`, so `AllCarts`, `AllCartItems` and `ItemLogs` observers can hold rows the server has deleted until something else refetches them. That refetch list is an open gap; `PantryData` / `ItemStocksForItem` **do** exist since Task 7 and **are** invalidated by the cascade, but are left out deliberately — every row it deletes belongs to the location being deleted, `PantryData` is keyed by `locationId` so the stale entry is unreachable, and the Stock-tab pager pages over the (refetched) location list. See the comment on `useDeleteLocation`.
- `useActiveLocation()` (`src/hooks/useActiveLocation.tsx`) - React Context hook exposing `{ activeLocationId, setActiveLocationId, activeLocation }`. The active id is persisted in localStorage under a **per-mode** key — `active-location-id:local` / `active-location-id:cloud` (`activeLocationStorageKey(mode)`) — and is re-read when the data mode changes, not only on mount. The two modes have disjoint id spaces (local seeds `DEFAULT_LOCATION_ID = 'local'`; cloud ids are server cuids), so a shared slot handed each mode the other's id. The legacy bare `active-location-id` key (`ACTIVE_LOCATION_STORAGE_KEY`) is read through as a fallback in local mode and migrated into the local slot once on mount, so an existing user is not reset. Once the list has loaded, an active id matching none of its entries falls back to the **`isDefault`** location (`locations.find((l) => l.isDefault)?.id ?? locations[0]?.id`) — not to the `'local'` literal, which names nothing in cloud. **No id is special-cased as always-valid**: the removed `activeLocationId === DEFAULT_LOCATION_ID` early return made `'local'` permanently "valid" in cloud, where every location-scoped query then returned empty — a silently empty pantry. A list that has loaded but is **empty** leaves the active id untouched (nothing to point at; an empty list is usually transient). The provider `ActiveLocationProvider` is mounted in `__root.tsx` (wraps the whole app) and reads the location list via `useLocations`. It also bootstraps shopping carts: whenever `activeLocationId` changes it ensures the no-vendor + per-vendor carts exist for that location. Local mode calls `bootstrapCarts(activeLocationId)` (Dexie) and then invalidates `['cart']` queries so any cart query that resolved before the bootstrap finished refetches. **Cloud mode does the same through the `bootstrapCarts(locationId: ID!)` mutation since PR 3b Task 4**, refetching `AllCarts` by name afterwards; that cloud effect is gated on the active id being in the loaded location list, because the `'local'` sentinel of a fresh session would be refused with `FORBIDDEN`. `VendorCart` is deliberately NOT refetched — that query creates its own cart when it is missing. This keeps `getCart` a pure read (see `db/operations.ts`) instead of lazily creating carts inside a `queryFn`. **LIVE (PR D):** the active location now scopes all stock-bearing data. Every data hook that reads/writes stock threads `activeLocationId` down to the operations layer (it appears in TanStack Query keys so switching the active location refetches): `useItems`/`useItem` (return a **joined `PantryItem`** = global `Item` + active-location `ItemStock` fields), `useItemSortData`, `useItemLogs`, the cart hooks (`useVendorCart`/`useAllActiveCarts`/`useLastPurchasedByVendor` — carts are per `location × vendor`), `useCreateItem`/`useUpdateItem` (split the per-location stock STATE into the active-location `ItemStock`; the global stock configuration stays on the `Item` — see the v16 note in `db/CLAUDE.md`), `useConsumeRecipes` (cooking), and `useCreateVendor` (pre-creates the vendor cart for the active location). When no `ActiveLocationProvider` is mounted (isolated unit/story renders), the hook returns a fallback pinned to `DEFAULT_LOCATION_ID` with a no-op setter, so tests don't need to wrap in a provider — that fallback keeps the sentinel deliberately: it has no location list to consult.

  **Cross-mode paths must NOT use `activeLocationId`.** Once the slot became per-mode, `useActiveLocation().activeLocationId` is *the current mode's* id, and the two id spaces are disjoint — so any code that hands one mode's id to the other mode's data layer is broken by construction. Import/export/migration are exactly that shape, and all three had passed the cloud id into a **local**-format slot; before the split they worked only because the cloud id happened to be the literal `'local'`, which is also a valid local location id. Two module-level helpers in `useActiveLocation.tsx` serve them:
  - `readStoredLocationId(mode)` — the same pure localStorage read the provider uses (legacy-key read-through included). Use where the id only has to *match a payload*: `ImportCard`'s cloud branch passes `readStoredLocationId('local')` to `resolveFlattenLocationId`, because a backup file is always local-shaped (`fetchCloudPayload` writes no `itemStocks`) so a cloud cuid can never name one of its locations — with one, every multi-location backup resolved to `null` and the import was refused outright. `usePostLoginMigration` passes it as `importCloudData`'s `locationId` for the same reason: it flattens the **local** payload.
  - `resolveLocalActiveLocationId()` — async; the local slot **validated against the local `locations` table**, falling back to the local `isDefault` row (then any row, then the sentinel). Use where the id is *written into local Dexie*: `DataModeCard`'s cloud→local copy (`doSwitch` / `doSignOut`) synthesises `ItemStock` rows, and a row under a nonexistent location id is unreachable — the user lands on an empty pantry after the reload.

  `usePostLoginMigration`'s `locationResolved` gate still validates the **cloud** active id against the **cloud** list (`useLocations()` is dual-mode). It no longer guards the copy target; whether the local slot should also be validated against the local table there is left to PR 4.
- `useCloudLocationId()` (`src/hooks/useCloudLocationId.ts`) - Returns an async `(explicit?: string) => Promise<string>` that resolves **at call time** the location a CLOUD write should target. Used by the cloud branches of `useCreateItem`, `useUpdateItem`, `useAddItemToLocation`, `useRemoveItemFromLocation`, `useAddInventoryLog` (PR 3a Task 4) and — since PR 3b Task 4 — `useCreateVendor` and `useConsumeRecipes`; local branches never touch it. **It exists because of a real bug** (found by cloud E2E, 2026-09-04): on a fresh cloud session there is no `active-location-id:cloud` slot, so `readStoredLocationId('cloud')` returns `DEFAULT_LOCATION_ID` — the `'local'` sentinel, which names no cloud `Location` — until `GetLocations` resolves and `ActiveLocationProvider` corrects it. A **read** in that window merely re-runs with the corrected id; a **write** is refused by `requireLocationRole` with `FORBIDDEN` and is lost. Creating an item from the pantry's Add dialog immediately after load created the `Item`, had its follow-up `upsertItemStock(locationId: 'local')` rejected, and left the dialog hanging with the item stocked nowhere — thirteen cloud E2E specs failed on it. The provider's correction cannot fix this on its own: `activeLocationId` is state, and a handler that has already started reads the value from the render it started in. So the write path asks Apollo directly (`GetLocations`, `cache-first`) — a cache hit costs nothing, a miss awaits the in-flight request instead of firing a doomed mutation. An `explicit` id (the Stock-tab pager's) is trusted and skips the read, since it can only have come from the loaded list. **It degrades rather than throws**: if the query yields no locations (a stubbed client, an offline cache) the current active id is returned unchanged, so nothing that worked before starts failing here. Pinned by the `a fresh cloud session, before GetLocations has resolved` block in `useItemStockWrites.cloud.test.tsx` — whose fixture removes the storage slot, because **every other test in that file seeds it with a real cuid and therefore pre-resolves the very thing that breaks.**
- `useCloudLocationKnown(activeLocationId, isCloud)` (`src/hooks/useCloudLocationKnown.ts`) - The READ-side counterpart of `useCloudLocationId`. Returns `true` in local mode, and in cloud mode only once `GetLocations` has a location matching `activeLocationId`. Every location-scoped cloud read is `skip`ped until then and reports `isLoading: true` — a skipped Apollo query reports `loading: false`, and calling that "loaded, nothing here" would flash an empty screen on every cloud page load. Two reasons it exists: the request would be a wasted `FORBIDDEN` (every `locationId` argument is now `ID!`, so there is no server-side fallback to absorb a bad id), and Apollo keeps the bad request as a live OBSERVER keyed by its variables — a mutation refetching BY NAME with `awaitRefetchQueries` then refetches the stale `{locationId: 'local'}` observer, fails again, and rejects a mutation that already succeeded. It lived inside `useItems.ts` from PR 2 until PR 3a Task 4 moved it to its own file, when the three inventory-log readers needed it too. Callers: `useItems` / `useStockedItems` (`PantryData`), `useItemLogs` (`ItemLogs`), `useItemSortData` (`LastPurchaseDates`), and — since PR 3b Task 4 — `useVendorCart` (`VendorCart`). It reads `useGetLocationsQuery` rather than `useLocations()` so it adds nothing to the local branch; Apollo dedupes it against `ActiveLocationProvider`'s own call, so the gate costs no request.
- `useStockedItems()` (`src/hooks/useItems.ts`) - Returns the **pantry's** data source: only items that have an `ItemStock` in the **active location**, joined as `PantryItem[]` (via `getStockedItems`). Items not stocked in the active location are absent. Switching the active location re-scopes the result (the active id is in the query key `['items', 'stocked', { locationId }]`). All seven pantry views (`PantryListView` + the three group + three detail views) use this instead of `useItems`. **Dual-mode since PR 2** — cloud derives it from the **same `PantryData` result `useItems` reads**, filtered to the items that have a row in `itemStocks`, so the two hooks cost one request between them and switching the active location re-scopes via a query VARIABLE rather than a query key. Contrast with `useItems()`, which returns **every** global `Item` joined with active-location stock (zeroed when not stocked) — used by the Add combobox catalog, cooking (to mark unavailable items), and shopping.
- `useItemSearchTail({ inGroupIds, query })` (`src/hooks/useItemSearchTail.ts`) - The shared tail behind every location-scoped item search. Reads the **global** catalog (`useItems()`), subtracts the ids the calling page already renders, and returns `{ inLocation, notStockedHere, hasExactGlobalMatch }`. `inLocation` is stocked in the active location but absent from the page's list; `notStockedHere` exists globally with no `ItemStock` here. **`inGroupIds` must be the page's own already-location-scoped list**, not raw group membership — an item carrying the group but stocked elsewhere belongs in `notStockedHere`, where one press stocks it here and promotes it straight into the page's list. `hasExactGlobalMatch` is true when any global item's name equals the query **including one already in the page's list**; callers pass it to `ItemListToolbar`'s `hasExactMatch` so the create affordance keys off the global catalog rather than the twice-filtered visible set — that is the #245 fix. **No mode branch (PR 2, Task 8).** The hook used to carry one isolated `isCloud` bypass that put every out-of-list match into `inLocation` and left `notStockedHere` empty; it was deleted once `useItems()` began joining cloud items against the active location's `ItemStock`, so bucket 3 is live in both modes. Memoize `inGroupIds` at the call site. **Callers should reach for `useItemSearchTailWiring` below instead of calling this directly** — it wraps this hook plus the view-agnostic wiring every page needs. **`useItems()` is called from inside this hook, not passed in as a parameter** — a deliberate PR B decision (carried forward from PR A's review). The obvious alternative, taking `items` from the caller, looked like it would save a redundant read on the pantry surfaces (which already call `useStockedItems()`), but it is actively wrong: the only list a pantry caller has to hand is the **stocked-here** set, and feeding that in as the "global catalog" would silently empty bucket 3 — exactly the location-blindness this feature exists to fix. The read this hook performs is also not redundant in practice: TanStack Query dedupes on the `['items']` key, and both `NewItemDialog` (mounted on the flat pantry) and the pantry views themselves already keep that query warm, so the extra call costs nothing measurable — shelf detail is the only surface that gains a genuinely new `getAllItems()` read per visit, the same read its sibling flat-pantry view already pays.
- `useItemSearchTailWiring({ inGroupIds, query, renderItem, sortTail?, groupAction?, groupNote? })` (`src/hooks/useItemSearchTailWiring.tsx`) - The shared VIEW-AGNOSTIC wiring behind every page's `ItemSearchTail` (extracted in PR B from the shopping cart page, which was the only caller until then; `PantryListView` and `ShelfDetailView` are PR B's two new callers; `VendorDetailView` and `RecipeDetailView` joined in PR C, completing the five surfaces — `shopping/$vendorId` plus those four). Calls `useItemSearchTail` for the two buckets, then: (1) owns the one-mutation-at-a-time pending id (`useState<string | null>`), injecting it into both action descriptors so a caller cannot forget it; (2) wraps a caller's `ItemSearchTailGroupAction.onAction` — **async**, `(item) => Promise<void>` — as `setPending(item.id); try { await onAction(item) } catch {} finally { setPending(null) }`, so pending clears regardless of outcome and callers use `mutateAsync` instead of hand-writing `{ onSuccess: clear, onError: clear }` pairs; (3) builds bucket 3's `addToLocationAction` itself (label `items.searchTail.addToLocation`, icon `<Plus />`, `onAction` calling `useAddItemToLocation().mutateAsync`), gated on `canAddToLocation = !!activeLocation` — **no mode term since PR 2 Task 8**, because `useAddItemToLocation` gained a cloud branch and the action now works in both modes; the gate is only "is there a resolved active location to add to" — and omits the key entirely (not a disabled action) when false; (4) applies the caller's `sortTail` to both buckets, or passes `useItemSearchTail`'s name order through unchanged if omitted. Returns `{ tailProps, hasTail, hasExactGlobalMatch }` — `tailProps` is a complete `ItemSearchTailProps`, spreadable straight into `<ItemSearchTail>`; `hasTail` is `hasVisibleTail(tailProps)` (exported from `ItemSearchTail.tsx`), the SAME derivation the component uses for its own early return, so a caller's empty-state guard and the component's suppression can never drift apart the way two independently-written booleans could. Bucket 2's `groupAction`/`groupNote` choice is NOT this hook's job — the calling page decides which one (or neither) to pass, e.g. the cart page passes `groupNote` for the no-vendor cart, `groupAction` once its vendor has resolved, and neither while the vendor id in the URL cannot be resolved (deleted-vendor window) — see `routes/CLAUDE.md`. `VendorDetailView` reproduces that same three-way split on the pantry side, and `RecipeDetailView` mirrors it for recipes.
- `useShowStock()` (`src/hooks/useShowStock.ts`) - Returns a `useCallback`-stable predicate `(item: { stockId?: string }) => boolean` = `isStockedHere(item)`, the **display gate** every search-tail row renderer passes to `ItemCard`'s `showStock`. A bucket-3 row exists globally with **no** `ItemStock` in the active location, so `joinItemStock()` hands it zeroed quantities and no `stockId` — rendering those zeros as real stock is a lie. **No mode branch and no mode dependency since PR 2 Task 8** — the hook no longer calls `useDataMode` at all. It used to short-circuit to `true` in cloud, back when cloud had no `ItemStock` backend and the gate would have blanked every row; since `useItems()` joins `PantryData` per location, a cloud item unstocked here carries `stockId: undefined` exactly as a local one does. Extracted in PR C from three verbatim copies (`PantryListView`, `ShelfDetailView`, `shopping/$vendorId`) that PR C's own two new views would have taken to five. Re-exported from `hooks/index.ts`, but every call site imports the deep specifier `@/hooks/useShowStock` — purely to match how the same files import `useItemSearchTailWiring`; nothing forces it. **Deliberately NOT adopted at the four *filter* call sites** (`useVendorCartCounts.ts`, `routes/cooking.tsx`, `routes/shopping/index.tsx`, `routes/shopping/$vendorId.tsx`), which call `isStockedHere(…)` directly. Those four carried an `isCloud ? … : …` bypass from PR 2 until **PR 3b removed it** — it was there for **carts and cooking**, not for items: a cloud `Cart` had no `locationId` and `consumeRecipes` wrote the caller's default location. They are still the wrong shape to adopt this hook at — `.filter(showStock)` reads as nonsense where the caller is selecting rows, not deciding whether to show stock figures on one. Those want a separately-named predicate (`useIsStockedInActiveLocation()`) adopted at all four at once; that is its own change.
- `useAddItemToLocation()` (`src/hooks/useItems.ts`) - Mutation that stocks an existing global item in a location via copy-on-add (`addItemToLocation` — inherits `targetQuantity`/`refillThreshold`/`dueDate`, with packed/unpacked → 0; there is no configuration left on a row to copy since v16). Takes `{ itemId, locationId? }` — `locationId` defaults to the active location, and the Stock-tab pager passes the location of the page being viewed. No-op-safe: returns the existing row without resetting quantities if the item is already stocked there. Invalidates `['items']` + `['itemStocks']`, **returned from `onSuccess` so `mutateAsync` resolves only once both refetches have landed** (see the awaited-invalidation note below). **Dual-mode since PR 2 Task 8** — cloud sends `addItemToLocation(itemId, locationId)`, whose resolver performs the same copy-on-add server-side; the `LOCAL_ONLY_LOCATION_MUTATION` throw is gone. The two modes' *source* defaults differ and are recorded rather than papered over: the cloud branch omits `sourceLocationId`, so the resolver copies from the item's most recently updated row, while local's parameter defaults to `DEFAULT_LOCATION_ID` and only falls back to the most-recent row when the item is not stocked there. No call site passes one in either mode. Cloud's cache handling is an `evictStockLists(cache)` **plus** a named `STOCK_LIST_QUERIES` refetch with `awaitRefetchQueries`, the cloud counterpart of the local awaited invalidation. Used by the pantry Add combobox's select-existing path and the Stock tab's "Add to location" CTA.
- `useRemoveItemFromLocation()` (`src/hooks/useItems.ts`) - Mutation that un-stocks an item from a location (`removeItemFromLocation`), cascading that location's inventory logs and its entries in that location's carts. Takes `{ itemId, locationId? }` — `locationId` defaults to the active location, and the Stock-tab pager passes the location of the page being viewed. The global `Item` survives: an item removed from its last location becomes an **orphan**, hidden from the pantry (`getStockedItems` filters on `ItemStock`) but still in the Add combobox catalog (`getAllItems`) and re-addable via `useAddItemToLocation`. Invalidates every family the cascade touches — `['items']` (pantry list, item reads, the item's logs), `['itemStocks']`, `['cart']`, `['sort']`, `['inventoryLogs']` and `['cartItems']` (the two per-item counts) — so removing from the **active** location leaves the UI consistent without a reload. **Dual-mode since PR 2 Task 8** — cloud sends `removeItemFromLocation(itemId, locationId)`. **Cloud cascades the same two families since PR 3c**: its resolver deletes the stock row, the item's inventory logs at that location, and the item's entries in that location's carts, all in one `prisma.$transaction`. Cart entries are found with the relation filter `cart: { locationId }`, reading `Cart.locationId` — the column the cart id is built from, not the id text. The cloud branch evicts the cached fields the cascade empties (`evictRemoveCascade`): both per-item counts, `itemLogs`, `inventoryLogs`, `lastPurchaseDates`, `cartItems` and `allCartItems`. So the Stock tab's confirmation line "Inventory logs: N · Cart entries: N" now renders in **both** modes.
- `useCreateItem(options?)` (`src/hooks/useItems.ts`) - Creates a global `Item` and, by default, an `ItemStock` for it in the **active location** (`createItem(input, activeLocationId)`). Passing `{ catalogOnly: true }` skips that `ItemStock` write, so the item lands in the catalog and is stocked **nowhere** — an intentional orphan (`getAllItems` surfaces it with `ZERO_STOCK` and no `stockId`; `getStockedItems` and therefore the pantry exclude it). The opt-in exists because the four Settings assignment tabs (`settings/{shelves,vendors,recipes,tags}/…/items`) edit a *global* item↔entity relation and must not write location-scoped stock, while the pantry's Add flow (`NewItemDialog`) must keep stocking here — hence opt-in rather than a changed default. **All four tabs pass the option to this hook directly**; none of them goes through `NewItemDialog`, which no longer takes a `catalogOnly` prop. **Honoured in BOTH modes since PR 2 Task 9**: cloud runs `createItem` and then, unless `catalogOnly`, an `upsertItemStock` in the active location — the same two steps in the same order as local's `createItem`. It returns the two joined through `joinItemStock`, so a caller reading `stockId` or a stock field off the result (`NewItemDialog`'s `onSuccess`, and through it the recipe-items dialog) sees the row just written rather than the `Item`'s inline columns, which PR 5 removes. **No caller passes `consumeAmount`** — a newly created item defaults to `1` in both modes (`createItem` in `db/operations.ts`, and the cloud `createItem` resolver), so it is valid on arrival and `ItemForm` opens it clean. The default lives in exactly those two places (one per data mode, which cannot share code); a call site that passes a literal would fork it. It was `0` between 2026-08-23 and 2026-08-24 — see `routes/settings/CLAUDE.md`.
- `useUpdateItem()` (`src/hooks/useItems.ts`) - Takes `{ id, updates, locationId? }`. In local mode the five per-location state fields (`packedQuantity`, `unpackedQuantity`, `targetQuantity`, `refillThreshold`, `dueDate`) are split into `locationId`'s `ItemStock` (defaulting to the active location) and everything else — identity **and** the eight global stock settings — is written to the `Item`, applying to every location at once; the Stock-tab pager passes the location of the page being viewed. **Cloud mode splits the same way since PR 2 Task 9**: `toConfigInput(updates)` goes to `updateItem`, and the five state fields go to `upsertItemStock(itemId, locationId ?? activeLocationId, …)`. A pure stock edit sends no `updateItem` at all; a pure configuration edit creates no `ItemStock` row where none existed. The five fields are **stripped** from `updateItem` rather than sent to both — `updateItem`'s own server-side dual-write targets the caller's *default* location, so leaving them inline would let a save in the Garage overwrite the Kitchen's row. The two Apollo mutations are separate because they touch different root fields: `updateItem` changes `ROOT_QUERY.items` (shared by `GetItems` and `PantryData`), while `upsertItemStock` changes `itemStocks` / `itemStocksForItem`, which a `GetItems` refetch never reaches. Invalidates `['items']` and `['itemStocks']` (it writes an `ItemStock` row, which the Stock pager reads back) — two keys, not the five the previous `onSuccess` wrote, because invalidation matches by **prefix**, so `['items']` already covers `['items', id]`, the per-tag/vendor counts, and both item lists (`useItems`, `useStockedItems`). Both are **returned from `onSuccess`**, so `mutateAsync` resolves only once the refetches have landed (see below).
- `useApplyUnitSwitch()` (`src/hooks/useItems.ts`) - Commits a unit switch as ONE Dexie transaction (`applyUnitSwitchBatch`): the `Item`'s global stock configuration, the converted quantities for **every** location, and the rewritten `defaultAmount` of every affected recipe. Takes `{ itemId, updates, locationId?, stockConversions, recipeUpdates }` — all arithmetic is the caller's, since the transaction may not await anything of its own. Invalidates every family it touched in one pass: `['items']` (+ `['items', id]` and the per-tag/vendor counts), `['itemStocks']`, `['recipes']` (+ `['recipes','itemCount']`) — a missed one shows up as a stale screen after a *successful* save, never as an error. **Dual-mode since PR 3c.** Cloud sends ONE `applyUnitSwitch` mutation, whose resolver does the same three groups of writes inside one `prisma.$transaction` — it has to be one mutation, because Apollo has no client-side transaction to borrow. Before PR 3c this hook threw `LOCAL_ONLY_UNIT_SWITCH`, because the cloud schema had **no `applyUnitSwitch` mutation at all**: the design named one (§2) and PR 1 shipped `itemStock.graphql` without it. Nothing failed, because `buildStockConversions` gated on `isLocal`, so the dialog listed no conversions for the cloud branch to write — a cloud unit switch simply left every location's quantities in the OLD unit. Used exclusively by the Info tab's unit-switch confirmation.
- `useInventoryLogCountByItem(itemId, locationId?)` / `useCartItemCountByItem(itemId, locationId?)` (`src/hooks/useItems.ts`) - Per-item counts of the two families `removeItemFromLocation` cascades. Passing `locationId` scopes each count to exactly the rows a removal from that location would delete; omitting it counts every location. The location is part of the query key, so the two scopes never share a cache entry. The Stock tab's remove confirmation uses the scoped form — an item-global count would over-report what is being deleted. **Both hooks are dual-mode since PR 3c**, so the confirmation line is no longer local-only. How each mode decides "in this location": local logs with an absent `locationId` read as the default location and local cart entries match on the parsed cart id; cloud logs filter on `InventoryLog.locationId` (NOT NULL since PR 3a) and cloud cart entries on the relation filter `cart: { locationId }`. `inventoryLogCountByItem` requires a location in cloud, so that branch is skipped when the caller omits one — only the local item-global count can answer without one.
- `useItemStock(itemId, locationId?)` / `useItemStocks(itemId)` / `useItemStocksForLocation(locationId?)` (`src/hooks/useItemStocks.ts`) - Raw `ItemStock` row reads. `useItemStock` returns the single (item × location) stock (defaults to the active location); `useItemStocks` returns every location's stock for an item; `useItemStocksForLocation` returns all stocks in a location. **Only `useItemStocks` is dual-mode** (PR 2): it backs the Stock tab's all-locations pager, and its cloud branch reads `ItemStocksForItem` — the **same document and variables `useItem` issues** for its own per-location row, so Apollo serves both from one request rather than the pager costing a second. `useItemStock` and `useItemStocksForLocation` have no cloud caller today and stay Dexie-only; the cloud reads they would need (`itemStocksForItem` filtered by location, and `itemStocks(locationId:)`) are both already in the schema. The joined stock that pages consume still comes via `useItems`/`useItem`; these expose the underlying rows.

**Awaited invalidation** — `useUpdateItem`, `useAddItemToLocation`, `useUpdateRecipe`, `useUpdateShelfMutation` and `useApplyShelfFilterPicks` (local branch only) **return** their `invalidateQueries` from the local `onSuccess` instead of firing and forgetting it; almost every other `onSuccess` in these hooks still fires and forgets. TanStack `await`s whatever `onSuccess` returns *before* it dispatches success (`query-core@5.90.20/mutation.js:123` — `await this.options.onSuccess?.(…)` sits above `#dispatch({ type: 'success' })`), so a caller's `await` resolves only once the refetch has landed, not merely once the write has. The search tail needs that: `useItemSearchTailWiring` re-enables every row in a `finally` after that `await`, and the recipe and shelf group actions append to an array captured from the render closure — re-enabled against stale data, two quick presses drop one. Each returns the fewest keys that cover the work, since invalidation matches by **prefix**. **Cloud branches are no longer uniformly asymmetric**: `useUpdateRecipe` and `useApplyShelfFilterPicks` both pass `awaitRefetchQueries`; `useUpdateItem`'s and `useUpdateShelfMutation`'s cloud branches do not.

**`mutate` sites are affected too — benignly.** They are not a separate code path: `useMutation` returns `mutate = (vars, opts) => observer.mutate(vars, opts).catch(noop)` and `mutateAsync = observer.mutate` (`react-query@5.90.20/useMutation.js:31-40`), the same function. The caller does not await the result, but everything the mutation *reports* is deferred behind the same awaited `onSuccess`: `isPending` stays true (it reads `state.status`, set by the success dispatch) and the per-call `{ onSuccess }` fires from the observer's success notification, both now landing after the refetch. Three surfaces see it, and each is an improvement rather than a regression — they now settle against fresh data:
- `routes/settings/shelves/$shelfId/index.tsx:64,82` / `:85,92` — `updateShelf.mutate(…, { onSuccess: () => goBack() })`: navigation happens after the `['shelves']` refetch, and the Save button (`:119-120`, bound to `updateShelf.isPending`) keeps spinning until then.
- `routes/items/$id/relation/vendors.tsx:40` — `updateItem.mutate` with no per-call callback; the per-badge spinner and its `pointer-events-none` (`:77,81`) and the `useEffect` that clears `togglingVendorId` (`:28-29`) all key off `updateItem.isPending`, so the badge stays busy one refetch longer.
- `routes/items/$id/relation/recipes.tsx:45` — the same shape for `updateRecipe.isPending` (`:33-34,80,84`).

**Regression guards — only three of the five returns are pinned.** `useUpdateRecipe` (`RecipeDetailView.test.tsx`) and `useUpdateShelfMutation` (`ShelfDetailView.test.tsx`) each have a test that goes RED when the `return` is dropped; both hold the relevant refetch open behind a `vi.mock` gate on its `queryFn` (`getRecipes` / `getShelf` — note `getShelf`, not `listShelves`: gating the `['shelves']` list would leave `['shelves', id]` free to refetch, so the row would be gone before the assertion) and assert the group-action button is still disabled. `useApplyShelfFilterPicks` (`useApplyShelfFilterPicks.test.tsx`) has the same shape of guard: it holds `getAllItems` open behind a `vi.mock` gate and asserts `mutateAsync` has not resolved until that refetch lands. **`useUpdateItem` (`useItems.ts:436`) and `useAddItemToLocation` (`useItems.ts:349`) have no such guard** — verified 2026-08-27: dropping either `return` leaves the whole web suite green. Their search-tail consumers are `VendorDetailView`'s bucket-2 action and the wiring hook's bucket-3 action, so a gate test there would have to hold `getAllItems`/`getStockedItems` open. Do not read the paragraph above as implying all five are pinned.
