# Custom Hooks

## Cloud read fetch policy

**Every cloud READ query in this app runs on `fetchPolicy: 'cache-and-network'`, with one named exception.**

Apollo's default is `cache-first`. That is wrong here because the cloud Apollo cache is
persisted to IndexedDB (`Player1InventoryCloudCache`) and restored **before React mounts**
(`main.tsx` → `bootstrap.ts` → `apollo/persistence.ts`). The snapshot has no TTL and no
schema version, so `cache-first` finds a complete answer in it and **sends no request at
all**. The data stays at whatever this device last saw. On an iOS home-screen PWA there is
no reload button and no pull-to-refresh, so nothing else asks either. Fixed 2026-09-22 —
see `docs/global/bugs/2026-09-22-bug-cloud-queries-cache-first.md`.

**The policy always comes in a pair.** With `cache-and-network` the network leg runs on
every mount and **fails offline**, so every cloud branch reports
`isError: !!cloud.error && !cloud.data` — never bare `!!cloud.error`. A failed refetch over
a good cache is not an error state; reporting one would put an error screen in front of
data the user can read, which is exactly what the offline work exists to prevent.

**The pair has a second half: `isLoading` must mean "nothing to show yet", not "a request
is in flight".** With `cache-and-network` Apollo hands back the restored snapshot AND keeps
`loading: true` until the network answers. Ten components return a spinner straight out of
`if (isLoading)` (`PantryListView.tsx:239`, `ShelfGroupView.tsx:151`,
`routes/items/$id.tsx:90` and seven more), so passing Apollo's `loading` through hid
readable data behind a spinner on every cloud mount. Every cloud branch now reports
`isLoading: cloud.loading && !cloud.data` — 24 sites across nine hook files. Use
`isFetching` when you want "a request is in flight"; `useItems` and `useStockedItems`
expose it (`cloud.networkStatus < 7`) and no component reads it yet.

**Never add `errorPolicy: 'all'`.** Measured on Apollo Client 4.1.6: the default `'none'`
leaves the cached result in `data` after a failed network leg, while `'all'` moves it to
`previousData` and leaves `data` **undefined** — it blanks the screen for an offline user.
It is pinned RED by tests in `useLocations.test.tsx` and `cloudFetchPolicy.cloud.test.tsx`.

**One query stays on `cache-first`, on purpose:**

| Query | Why |
|---|---|
| `useCloudLocationKnown` (`GetLocations`) | Observes the same document and variables as `useLocations`, so it rides that hook's cache write for free. |

There used to be a second one. `useLastPurchaseDate` ran once per `ItemCard` with
`itemIds: [one]`, and `lastPurchaseDates` is keyed by `['itemIds','locationId']`
(`apollo/cloudCache.ts`), so every card owned a separate cache entry that deduplication
could not merge — `cache-and-network` there would have sent one request **per visible
card**. It was pinned to `cache-first` and left knowingly stale instead. **Deleted in
#305.** `ItemCard` now takes `lastPurchaseDate` as a required prop, fed from
`useItemSortData`'s batch query, so the batch is the only `LastPurchaseDates` query in the
app and every card's date refreshes with the list.

**Coming back to the app refetches every active query. There is no opt-out.**
`cache-and-network` refreshes a query when its component **mounts**, and resuming a
backgrounded PWA mounts nothing — so an app left open stayed as stale as the moment it was
last opened. `apollo/ApolloWrapper.tsx` handles this: its `visibilitychange` listener (which
already saved the cache on hide) calls `client.refetchQueries({ include: 'active' })`
when the app becomes visible. Three rules, all pinned by tests in `ApolloWrapper.test.tsx`:

| Rule | Why |
|---|---|
| Online only (`isOffline()` returns early) | Every request would fail. The hooks keep showing cached data either way, and the failures cost battery and mobile data. |
| At most once per `RESUME_REFETCH_MIN_GAP_MS` (30 s) | People switch apps constantly on mobile. Rows cannot meaningfully change in a shorter gap. |
| The gap clock starts at **mount**, not at 0 | Every query on screen already ran a network leg at mount, so a glance away and back a few seconds after launch must not fire a second round. |

**The opt-out that used to be here is gone (#305).** Two constants in
`apollo/constants.ts` let a query set a `context` marker that `onQueryUpdated` skipped.
They existed only because `useLastPurchaseDate` ran one `LastPurchaseDates` query per
`ItemCard`: a pantry of 40 items sent 40 requests on every resume. Measured with a counting `ApolloLink`, 20 cards produced 20 requests. `ItemCard`
now receives the date as a prop, so the only `LastPurchaseDates` query on screen is
`useItemSortData`'s single batch one and refetching everything costs one request.
`ApolloWrapper.test.tsx` (`ApolloWrapper resume refetch cost`) measures real requests
through a counting link and pins that the count does **not** grow with the number of
cards: 3 cards and 30 cards both send 1 request at mount and 1 more on resume.

It stamps no `setLastSyncedAt`: `save()` already stamps every 5 seconds while online, so a
stamp here would be replaced by a coarser one within five seconds. Local mode is untouched
— the effect returns early on `!userId`, so the listener is never attached.

This is also why the `isLoading` guard above is not optional. A refetch sets `loading` true
again while keeping `data`, so without the guard every resume would drop a spinner over the
pantry the user was reading. Pinned by `cloudFetchPolicy.cloud.test.tsx` → `a resume
refetch does not put a spinner over the pantry`.

**Two hooks reading one document still cost one request.** `useItems`/`useStockedItems`
(`PantryData`), `useItem`/`useItemStocks` (`ItemStocksForItem`) and
`useAllActiveCarts`/`useLastPurchasedByVendor` (`AllCarts`) each carry the policy on both
halves. Apollo's `queryDeduplication` (on by default, never disabled in
`apollo/client.ts`) collapses the identical in-flight operation. Measured in
`cloudFetchPolicy.cloud.test.tsx` → `two hooks on one document still cost one request`.
One exception since 2026-11-01: if a mutation answers while that shared request waits, the
request is sent again, up to `MAX_QUERY_ATTEMPTS` sends in total (see
`apollo/staleReadRetryLink.ts`). So "one request" holds only while no save lands during the
wait.
Giving the network leg to only one of a pair would work too, but then the pair breaks the
moment the other half mounts alone.

**The one cloud read outside `src/hooks/`** is `useAllCartItemsQuery` in
`routes/shopping/index.tsx`. Its policy is pinned by an options-capture test in
`routes/shopping/index.cloud.test.tsx` instead of the real-Apollo fixture the hooks get.

**Navigation:**
- `useAppNavigation()` (`src/hooks/useAppNavigation.ts`) - Tracks navigation history in sessionStorage, provides `goBack()` function for smart back navigation to previous app page (fallback to home). Uses `router.history.push(previousUrl)` to preserve full URL (including search params) when going back.
- `useNavigationTracker()` (`src/hooks/useNavigationTracker.ts`) - Global hook (used in `__root.tsx`) that records every page visit as a full URL (`pathname + searchStr`) in sessionStorage. When params change on the same page, updates the last entry in place rather than appending a new one.
- `useIsDesktop()` (`src/hooks/useIsDesktop.ts`) - `true` when the screen is at least the Tailwind `lg` width. It reads `matchMedia('(min-width: 64rem)')` through `useSyncExternalStore`, so JavaScript and the `lg:` classes switch at the same width. Returns `false` when `matchMedia` is missing. Use it only where the width changes what renders (the `/settings` redirect, `isFullscreenPage(pathname, { desktop })`); use `lg:` classes for styling. `src/test/setup.ts` mocks `matchMedia` as always `false`, so tests get the mobile answer; call `mockScreen({ desktop: true })` from `src/test/viewport.ts` for the desktop one.

**Item List State:**
- `useUrlSearchAndFilters()` (`src/hooks/useUrlSearchAndFilters.ts`) - Manages search query, tag filter state, vendor/recipe filter state, and UI visibility (filters panel, tags visible) via URL params (`?q=`, `?f_<typeId>=`, `?f_vendor=id1,id2`, `?f_recipe=id1,id2`, `?filters=1`, `?tags=1`). Uses `router.history.replace` to update params in place (same history entry). Note: `filterState` only contains tag type filters — `vendor` and `recipe` keys are reserved and excluded from `filterState`. Exposes `selectedVendorIds: string[]`, `selectedRecipeIds: string[]`, `toggleVendorId(id)`, `toggleRecipeId(id)`, `clearVendorIds()`, `clearRecipeIds()`.
- `useSortFilter(storageKey)` (`src/hooks/useSortFilter.ts`) - Manages sort field and direction via localStorage key `${storageKey}-sort-prefs`. Used by all item list pages for per-page sort persistence. Accepts optional `defaultSortBy` option (defaults to `'name'`).
- `useScrollRestoration(key, scrollRef)` (`src/hooks/useScrollRestoration.ts`) - Saves/restores the scroll position of a scroll container element for a given key (typically the full URL). The app shell pins `<main>` to the viewport so the window never scrolls — list views scroll inside an inner `overflow-y-auto` container, so the hook operates on `scrollRef.current.scrollTop` / `.scrollTo`, not `window`. Saves scroll on component unmount (SPA navigation away); restores after data loads. Usage: attach a `useRef<HTMLDivElement>(null)` to the scroll container, call with `currentUrl` from `useRouterState` + the ref, then call `restoreScroll()` in a `useEffect` conditioned on `!isLoading`. For the 4 detail-page Items tabs (tags/vendors/recipes/shelves) the scroll container is owned by `LayoutInnerPages` and shared via `<Outlet>`; those callers read the ref from `useInnerPageScrollRef()` (a context exposed by `LayoutInnerPages`).

**Data Utilities:**
- `useVendorItemCounts()` (`src/hooks/useVendorItemCounts.ts`) - Returns `Map<vendorId, number>` of item counts per vendor, memoized with useMemo for performance
- `useTagItemCounts()` (`src/hooks/useTagItemCounts.ts`) - Returns `Map<tagId, number>` of global item counts per tag, memoized off `useItems()` + `useTags()`. Every tag gets an entry, including zeros. **Counts expand descendants** (`getTagAndDescendantIds`, the same walk `lib/shelfUtils.ts` uses): the shelf tag filter selects a tag *and all its descendants*, so a direct-assignment count would report 0 for a parent tag that in fact selects a dozen items. An item carrying both a parent and its child counts **once**. Location-unaware by design — these are global item↔tag relations. Distinct from the per-id `useItemCountByTag` (one async query per id, direct assignments only), which cannot be called in a badge loop.
- `useRecipeItemCounts()` (`src/hooks/useRecipeItemCounts.ts`) - Returns `Map<recipeId, number>` of global item counts per recipe, memoized off `useItems()` + `useRecipes()`. Every recipe gets an entry, including zeros. Recipes have no hierarchy, so membership is plain (mirrors the recipe branch of `lib/shelfUtils.ts`); counting from the item side also drops recipe entries pointing at deleted items. Location-unaware by design. The map-shaped counterpart to the per-id `useItemCountByRecipe`.
  - All three map-shaped count hooks are consumed together by the shelf filters tab (`settings/shelves/$shelfId/filters.tsx`), where each tag/vendor/recipe badge renders `` ` (${count})` `` after the name.
- `useItemSortData(items)` (`src/hooks/useItemSortData.ts`) - Returns `{ quantities, expiryDates, purchaseDates }` for sort operations on item lists. `quantities` is a `useMemo` (synchronous, no race condition). Local mode: `expiryDates` and `purchaseDates` are TanStack Query queries under the `['sort', ...]` key namespace. Cloud mode: uses `useLastPurchaseDatesQuery` (Apollo batch query) with `locationId: activeLocationId` and derives expiry dates synchronously — no TanStack Query involved. `lastPurchaseDates(locationId:)` is `ID!` since PR 3a Task 4, so the cloud query is gated on `useCloudLocationKnown`. Used by all five item list pages, by `routes/cooking.tsx`, and by the four Settings assignment tabs. Checkout explicitly invalidates `['sort', 'purchaseDates']` after purchase (local mode) and evicts the `lastPurchaseDates` root field (cloud mode). **`purchaseDates` also feeds every `ItemCard`'s `lastPurchaseDate` prop since #305** — the card fetches nothing of its own, so this is the ONLY `LastPurchaseDates` query in the app. Search-tail rows in bucket 3 (not stocked here) are absent from the map, so they get `undefined`; that matches the old per-card query, and their expiry chip is hidden anyway because it also needs `currentQuantity > 0`.
- `useItemLogs(itemId)` (`src/hooks/useInventoryLogs.ts`) - Returns inventory log entries for an item **at the active location**. Dual-mode: local uses TanStack Query + Dexie (`getItemLogs(itemId, activeLocationId)`, with the location in the query key); cloud uses `useItemLogsQuery` with `variables: { itemId, locationId: activeLocationId }`. **`itemLogs(locationId:)` is `ID!` since PR 3a Task 4** — there is no server-side default-location fallback any more, so the cloud branch is gated on `useCloudLocationKnown` and stays `isLoading` until `GetLocations` confirms the active id is a real cloud `Location`. Two-location proof: `useInventoryLogs.cloud.test.tsx`.
- `useAddInventoryLog()` (`src/hooks/useInventoryLogs.ts`) - Mutation hook to add an inventory log entry. Dual-mode: local calls `addInventoryLog` with the active location's id threaded in (matches the read side, `useItemLogs`, which filters by `activeLocationId`); cloud calls `useAddInventoryLogMutation` with a `locationId` resolved **at call time** by `useCloudLocationId()`, never the render-time active id. `addInventoryLog(locationId:)` is `ID!` since PR 3a Task 4: a write sent with the `'local'` sentinel is refused with `FORBIDDEN` and lost, and unlike a read it does not self-correct. Pinned by the `a fresh cloud session, before GetLocations has resolved` block in `useInventoryLogs.cloud.test.tsx`, whose fixture removes the `active-location-id:cloud` slot. The cloud branch sends **no `refetchQueries`** — nothing to target, and refetching `ItemLogs` by NAME would refetch every observer carrying that name.
- `useConsumeRecipes()` (`src/hooks/useRecipes.ts`) - Batch mutation hook for cooking done. Sends all item quantity updates, inventory logs, and recipe `lastCookedAt` stamps in a single call. Dual-mode: local uses `consumeRecipesBatch` (Dexie transaction); cloud calls `useConsumeRecipesMutation` (Apollo). **`ConsumeRecipesInput.locationId` is `ID!` since PR 3b Task 4**, and the cloud branch resolves it **at call time** with `useCloudLocationId()` — the `'local'` sentinel of a fresh cloud session would lose the whole cook to `FORBIDDEN`. Used exclusively by the cooking page `handleConfirmDone`. **Since households H3b task B.6 each item is `{ itemId, delta, note?, logKey?, logParams? }`** (`ConsumeRecipeItem`), where `delta` is minus the amount used. The cloud branch sends only that; the server computes the new stock and the log total in one transaction. The local branch computes them itself from `localStock` (the page's joined stock rows) with `consumeItem` and `getPackedTotal`, exactly as `cooking.tsx` did before, and hands finished rows to `consumeRecipesBatch`. Pinned by `useRecipes.test.ts` (local numbers, an item that opens a package) and `routes/cooking.cloud.test.tsx` (the cloud payload, with `toEqual`). **The changed input breaks cooking for a cloud client on an old bundle** until it reloads; the owner accepted this (H3b design, *Deploy*).

**Shopping:**
- `useVendorCartCounts()` (`src/hooks/useVendorCartCounts.ts`) - Returns `Map<vendorId, { count: number; inactiveCount: number }>` for the `/shopping` index cards + the `'count'` sort. `count` is items with this vendor stocked in the **active location**; `inactiveCount` is the subset with `targetQuantity === 0`. **No mode branch since PR 3b** — cloud used to keep a global tally and hard-code `inactiveCount: 0`, because a cloud `Cart` had no `locationId` and the count would not have matched the cart the card opened. PR 3a added the column and PR 3b re-keyed `Cart.id`, so both modes count the same way. Distinct from `useVendorItemCounts()` below, which stays global/location-unaware for `/settings/vendors` — vendor management is location-independent, so the two pages showing different counts for the same vendor is expected, not a bug (see `apps/web/src/routes/CLAUDE.md`).
- `useVendorCart(vendorId: string | null)` (`src/hooks/useShoppingCart.ts`) - Gets the active location's cart for a specific vendor (null = "No vendor" cart). Local: TanStack Query keyed `['cart', 'vendor', vendorId, { locationId }]`; `getCart` is a pure read — carts are bootstrapped up front by `ActiveLocationProvider` (see `useActiveLocation()` below), not created lazily here. Cloud: `vendorCart(vendorId, locationId)`, with `locationId` **`ID!` since PR 3b Task 4**. That query CREATES the cart when it is missing for a `participant` or higher; since households H5 task F.2 it needs only `viewer`, and a viewer gets an unsaved empty cart with the same id. The cloud branch is therefore gated on `useCloudLocationKnown` and stays skipped until `GetLocations` confirms the active id.
- `useAllActiveCarts()` (`src/hooks/useShoppingCart.ts`) - Returns the **active location's** carts (one per vendor plus the no-vendor cart). Local: TanStack Query keyed `['cart', 'all-active', { locationId }]`. Cloud: the whole-account `allCarts` query, narrowed client-side to the carts whose `parseCartId(id).locationId` is the active one — never by `id.startsWith(locationId + ':')`, because a location id is not a prefix-free code.
- `useCheckout()` (`src/hooks/useShoppingCart.ts`) - Mutation hook for "bought it all". Dual-mode: local calls `checkout` (`src/db/operations.ts`); cloud calls `useCheckoutMutation`. **Since households H3b task B.5 the cloud mutation takes the rows the screen showed, not totals.** `items: [CheckoutItemInput!]!` is one `{ cartItemId, quantity }` per cart row being bought, where `quantity` is the amount the screen showed. The server runs the whole checkout in one transaction, buys exactly those rows (whoever added them), and computes every inventory log total itself with `getPackedTotal` from `@p1i/types`. If the shared cart changed after the screen loaded, it refuses with the error code `CART_CHANGED` and writes nothing.
  - **The caller picks the rows.** `routes/shopping/$vendorId.tsx` sends `cartItems.filter(isBeingBought)` for the whole cart, not only the rows the vendor filter shows: the server refuses a list that leaves a row out.
  - **On `CART_CHANGED` the hook reloads the cart, then rethrows.** It re-reads `CartItems` for that cart with `network-only` (the cache entry `useCartItems` watches), and drops any error from that reload so it cannot hide the refusal. `isCartChangedError(err)` (exported from the same file) reads `extensions.code`. The page then closes the dialog and shows `shopping.cartChanged` as a toast. Tested in `useShoppingCart.test.ts` (reload) and `routes/shopping/$vendorId.checkout.test.tsx` (message). Only `mutateAsync` is tested; the page does not call `mutate`.
  - **The local branch is untouched.** Local mode has one user, and `checkout` in `src/db/operations.ts` reads its own cart and stock, so `items` is destructured off nowhere in the local `mutationFn`.
  - **`buildCheckoutLogQuantities` was deleted on `feature/households-h3b`.** From issue #336 until task B.5 the page used it to send each item's post-purchase total, because the resolver did not read `amountPerPackage`. After task B.5 no production code called it, so it and its 6 tests in `src/lib/checkoutQuantities.test.ts` were removed. The rule now lives in the server's `checkout` (`apps/server/src/resolvers/cart.resolver.ts`): the log total is `getPackedTotal` of the saved stock row. The describe block "checkout logs the on-hand total, computed on the server" in `apps/server/src/resolvers/cart-checkout.resolver.test.ts` pins it with hand-worked numbers (3.5, 3 and 6). Local mode computes the same number in `checkout` (`src/db/operations.ts`).
  - **`isBeingBought` and the server's SQL filter must agree.** `isBeingBought` (`packages/types/src/index.ts`, re-exported through `@/types`) picks the rows the web sends; the server reads `quantity: { gt: 0 }`. If they disagreed, every checkout of a cart holding the row in question would be refused with `CART_CHANGED`. `apps/server/src/lib/isBeingBought.test.ts` pins the function's answers. Local mode filters `ci.quantity > 0` itself in `src/db/operations.ts` and is not wired to it.
  - **The changed input breaks checkout for a cloud client on an old bundle** (it still sends `itemId`), until the user accepts the service-worker update prompt. The owner accepted this on 2026-11-15 (H3b design, *Deploy*).
  - **Test files DO type-check, so `tsc` finds a call site that forgets `items`** — since 2026-10-30 (issue #340). It does NOT find an old `{ itemId, quantity }` literal inside an untyped mock; grep for those by hand.
- `useLastPurchasedByVendor()` (`src/hooks/useShoppingCart.ts`) - Returns a `Map<string | null, Date | null>` of each vendor cart's `lastPurchasedAt` (the `null` key is the no-vendor cart). Drives the `'recent'` sort on the shopping index. **Dual-mode, and both branches now do the same thing.** Local: TanStack Query keyed `['cart', 'last-purchased-by-vendor', { locationId }]`, reading the active location's carts and keying by `parseCartId`'s `vendorId`. Cloud: derived from the **same `useAllCartsQuery`** `useAllActiveCarts()` runs, so Apollo serves it from cache (no extra round trip) and `useCheckout()`'s existing `AllCartsDocument` refetch keeps it fresh; it drops carts at other locations and keys by `parseCartId`'s `vendorId` too. **Cloud cart ids stopped being bare in PR 3b** — they are `${locationId}:${vendorId | 'no-vendor'}` like local ones, and the old comment saying `parseCartId` must not be used here was true before the re-key and false after it. Without the location filter one vendor's two carts would both write the same map key and the later one would win, so the page would sort by another location's purchase date.

**Cloud / Auth:**
- `usePostLoginMigration({ isLoaded, isSignedIn, household })` (`src/hooks/usePostLoginMigration.ts`) - Cloud mode only. Detects when a signed-in user has local IndexedDB items and has not been prompted before (localStorage `migration-prompted` key). Exposes `state: MigrationState`, `error: { forbidden, role, message } | null`, `dismiss()`, `confirmCopy()`, `declineCopy()`, `waitingStrategy`, `importData(conflictResolution)`, `chooseLocation(target)`, `cancelLocation()` and `pendingPayload`. `importData` calls `fetchLocalPayload()` then `importCloudData()` to migrate local data to cloud. Used by `PostLoginMigrationDialog`.
  - **Two ways the question is held back without turning it off** (since 2026-11-19, `docs/global/bugs/2026-11-19-bug-join-turns-off-copy-prompt.md`). (1) `paused` (optional input): the hook does nothing and stores nothing. `__root.tsx` passes `isCopyPromptPausedPath(pathname)` through `PostLoginMigrationDialog`, which is `true` on `/join/…` and `/sign-in`. (2) `migration-skip-households` (`MIGRATION_SKIP_HOUSEHOLDS_KEY`), a JSON list of household ids. The join page adds the household it joins with `skipCopyPromptIn(id)` (owner decision O12-A). While the list is not empty the hook waits for `household.id`, and does nothing in a listed household: neither the prompt nor a stored copy's question, and the stored strategy stays. In any other household it runs as before. Why not `canCopyInto`: a manager may copy, so a role check would still offer the copy into a household joined as manager. Until that date "Sign in to join" set `migration-prompted`, which stopped the question on the device in every later household too.
  - **A stored copy asks first** (owner decision O22-A, H5b decision T31). `household` is `{ id, name, role }` or `undefined` (loading, or no household). The `id` is read only by the skip list above. With a stored `migration-strategy` the hook waits until `GetLocations` AND `household` have loaded, then sets state `'confirming'` with the strategy in `waitingStrategy`. Nothing is sent before an answer. `confirmCopy()` runs the stored copy (the old auto-import body). `declineCopy()` removes `migration-strategy` and sets `migration-prompted`. `canCopyInto(role, strategy)` (exported) says whether to offer the copy: owner always, manager not for `clear`, member never. **Since 2026-11-19 the prompting path waits for `household` too** (not for `GetLocations`), because the dialog names the household and reads `canCopyInto(role, 'skip')` there as well (`docs/global/bugs/2026-11-19-bug-manual-import-names-no-household.md`). It stores nothing while it waits. Before O22-A a person in no household waited silently (`GetLocations` fails with `NO_HOUSEHOLD`) and the copy then ran into the next household, a shared one included.
  - **The copy asks "Import into which location?" first** (households H4 task E.4, decision O3). Local data always has `'local'`, so both paths (the Import button and the auto-import after a stored `skip` / `replace` strategy) stop in state `'choosing-location'` with the payload in `pendingPayload`. `chooseLocation(target)` runs the copy into that location; `cancelLocation()` copies nothing, removes `migration-strategy` and goes back to `'prompting'`. A stored `clear` does not ask (decision O2). There is no localStorage key to skip the question: an E2E spec answers the dialog in the page. `error.role` is a refusal for the household role (`importErrorKind`, decision T17).
  - **`MigrationState` includes `'error'`, and both copy paths now reach it** (the import ownership guard, issue #327). Before that the two paths swallowed every failure: the auto-import's `.catch` set `'done'`, so the dialog closed as if the copy had worked and the user was left in a half-copied cloud account with no message; and `importData` had no `catch` at all, so a failure was an unhandled promise rejection and the dialog stayed on `'importing'` for the rest of the session. `error.forbidden` comes from `isForbiddenImportError` (`lib/importData.ts`) — the one detector, shared with `ImportCard`, which reads `extensions.code` and never the message text. The `'error'` state keeps removing `MIGRATION_STRATEGY_KEY` (so the failure cannot loop) and keeps `MIGRATION_PROMPTED_KEY` unset (so a refresh can retry). **The local read that decides whether to prompt (`getAllItems()`) has a `.catch` since 2026-11-18** (`docs/global/bugs/2026-11-18-bug-post-login-migration-unhandled-read.md`). Before that a blocked or closed IndexedDB gave an unhandled rejection. The catch logs with `console.error`, sets no state (it stays `'idle'`, no dialog) and leaves `MIGRATION_PROMPTED_KEY` unset, so the next run of the effect or a refresh reads again. Pinned by `a failed local read` in `usePostLoginMigration.test.ts`.
  - **Once a copy has started, the effect does nothing** — since 2026-10-31. The `importStarted` ref is set when the stored copy's question opens (since O22-A; when the auto-import started, before) and when `importData` starts, and the effect returns early on it. Before that, the prompting branch called `setState('prompting')` on every effect re-run and replaced a state that `importData` or a failed auto-import had set. The effect's deps are `isLoaded`, `isSignedIn`, `locationsLoaded` and (since O22-A) `householdLoaded` (`apolloClient` left them then: the effect no longer starts the copy), and the live trigger is `locationsLoaded` going from unknown to known. **The copy itself causes that flip**: `importCloudData` ends with `client.resetStore()`, which makes `GetLocations` data undefined and then defined again. So a failed copy showed its error for about 100 ms and then the prompt came back. See `docs/global/bugs/2026-10-31-bug-cloud-copy-aborted-on-pantry.md`. Before PR 3c this hook threw `LOCAL_ONLY_UNIT_SWITCH`, because the cloud schema had **no `applyUnitSwitch` mutation at all**: the design named one (§2) and PR 1 shipped `itemStock.graphql` without it. Nothing failed, because `buildStockConversions` gated on `isLocal`, so the dialog listed no conversions for the cloud branch to write — a cloud unit switch simply left every location's quantities in the OLD unit. Used exclusively by the Info tab's unit-switch confirmation.
- `useInventoryLogCountByItem(itemId, locationId?)` / `useCartItemCountByItem(itemId, locationId?)` (`src/hooks/useItems.ts`) - Per-item counts of the two families `removeItemFromLocation` cascades. Passing `locationId` scopes each count to exactly the rows a removal from that location would delete; omitting it counts every location. The location is part of the query key, so the two scopes never share a cache entry. The Stock tab's remove confirmation uses the scoped form — an item-global count would over-report what is being deleted. **Both hooks are dual-mode since PR 3c**, so the confirmation line is no longer local-only. How each mode decides "in this location": local logs with an absent `locationId` read as the default location and local cart entries match on the parsed cart id; cloud logs filter on `InventoryLog.locationId` (NOT NULL since PR 3a) and cloud cart entries on the relation filter `cart: { locationId }`. `inventoryLogCountByItem` requires a location in cloud, so that branch is skipped when the caller omits one — only the local item-global count can answer without one.
- `useItemStocks(itemId)` (`src/hooks/useItemStocks.ts`) - Raw `ItemStock` row reads: every location's stock for one item. **Dual-mode** (PR 2): it backs the Stock tab's all-locations pager, and its cloud branch reads `ItemStocksForItem` — the **same document and variables `useItem` issues** for its own per-location row, so Apollo serves both from one request rather than the pager costing a second. The joined stock that pages consume still comes via `useItems`/`useItem`; this exposes the underlying rows.
  - **`useItemStock(itemId, locationId?)` and `useItemStocksForLocation(locationId?)` were deleted on 2026-10-07.** Both were Dexie-only with no caller anywhere — no component, no test, no story — and `hooks/index.ts` does `export * from './useItemStocks'`, so both sat on the public barrel surface while reading Dexie in cloud mode too. The `operations.ts` functions they called (`getItemStock`, `getItemStocksByLocation`) were **kept**: both still have production callers inside `operations.ts` itself.

**Awaited invalidation** — `useUpdateItem`, `useAddItemToLocation`, `useUpdateRecipe`, `useUpdateShelfMutation` and `useApplyShelfFilterPicks` (local branch only) **return** their `invalidateQueries` from the local `onSuccess` instead of firing and forgetting it; almost every other `onSuccess` in these hooks still fires and forgets. TanStack `await`s whatever `onSuccess` returns *before* it dispatches success (`query-core@5.90.20/mutation.js:123` — `await this.options.onSuccess?.(…)` sits above `#dispatch({ type: 'success' })`), so a caller's `await` resolves only once the refetch has landed, not merely once the write has. The search tail needs that: `useItemSearchTailWiring` re-enables every row in a `finally` after that `await`, and the recipe and shelf group actions append to an array captured from the render closure — re-enabled against stale data, two quick presses drop one. Each returns the fewest keys that cover the work, since invalidation matches by **prefix**. **Cloud branches.** Seven cloud writes wait for their reads with `refetchAfterWrite` (next paragraph): `useCreateItem` (stock step), `useAddItemToLocation`, `useRemoveItemFromLocation`, `useUpdateItem` (stock step only), `useApplyUnitSwitch`, `useUpdateRecipe` (both `mutate` and `mutateAsync`) and `useApplyShelfFilterPicks`. `useUpdateItem`'s configuration write (`updateItem`, with `refetchQueries: [GetItems]` on the hook) does NOT wait for its `GetItems` refetch, and neither does `useUpdateShelfMutation`. (Until 2026-11-18 this said `useUpdateItem`'s cloud branch does not pass `awaitRefetchQueries`. That was half wrong: its stock step did.)

**Reading again after a cloud write** — `src/apollo/refetchAfterWrite.ts`, since 2026-11-18 (`docs/global/bugs/2026-11-18-bug-failed-refetch-rejects-saved-write.md`). With `awaitRefetchQueries: true` Apollo 4.1.6 waits for the refetches with `Promise.all` (`core/QueryInfo.js`, `markMutationResult`), so ONE failed read REJECTED a write the server had saved, and the page showed the save as failed (a create retried this way made a second item). Now the hook sends the mutation with no `refetchQueries` and then awaits the helper:

| Entry form | What the helper does | Read when nothing is mounted? |
|---|---|---|
| a name (`'ItemStocksForItem'`) or a document | `client.refetchQueries({ include })` | no, only mounted queries |
| `{ query, variables }` | `client.query({ query, variables, fetchPolicy: 'network-only' })`, written to the cache | **yes**, the same as the old legacy form in a mutation's `refetchQueries` (`QueryManager.js`, `getObservableQueries`, which makes a `network-only` `ObservableQuery` for it) |

Every read gets `.catch(() => {})`, and the helper awaits them all, EACH on its own. For the names and documents it waits for each promise in `client.refetchQueries(...).results`, not for the returned promise: that one is a `Promise.all`, which rejects as soon as one read fails while the others are still open (fixed 2026-11-19, review of households H5c task H.4; pinned in `apollo/refetchAfterWrite.test.ts`). So the call still resolves only once the lists are read again, a failed read does not reject it, and a failed WRITE still rejects (it throws before the helper runs). A watched query keeps its own error. **Keep `PantryData` as `{ query, variables }`**: by name Apollo reads again every `PantryData` observer, also one `skip` parked on `{ locationId: 'local' }`, which sends a `FORBIDDEN` request (`stockListRefetches` in `useItems.ts`). Each hook's `update: evictStockLists` is unchanged; it still runs inside the mutation. Hooks call `useRefetchAfterWrite()`, which also returns `isRefetching`, and report `isPending: loading || isRefetching`: under `awaitRefetchQueries` the mutation's `loading` stayed true until the reads landed, and the relation tabs keep a badge busy on `isPending`. The Members hooks call the plain function. **A test that drives these hooks through `MockedProvider` must unmock `@apollo/client/react`**: `src/test/setup.ts` stubs `useApolloClient`, and the stub's `query` resolves `{ data: {} }` without reaching the mocks (`useItemSearchTailWiring.cloud.test.tsx` needed this). Pinned by the "whose refresh fails" describes in `useItemStockWrites.cloud.test.tsx` and `useItemLocationMutations.cloud.test.tsx`, and by `useUpdateRecipe.cloud.test.tsx` and `useApplyShelfFilterPicks.cloud.test.tsx`; each has controls that go red when the await is removed. **`isPending` is pinned for all ten hooks** in `refetchPending.cloud.test.tsx` (since 2026-11-19; the three location role hooks of households H5c task H.4 joined the seven, each with `GetHouseholdLocations` mounted beside it, because they read again by document): it is true while the write is in flight, still true after the write is answered while the read is held open, and false once the read lands or fails. The read is held by `createHoldLink` (`src/test/holdLink.ts`), a link put in front of a `MockLink` that keeps a named operation open until the test calls `release` or `fail`. Dropping `|| isRefetching` from one hook turns only that hook's 2 tests red (from the three location role hooks: 6 red); making `useRefetchAfterWrite` not await, or not count, turned all 14 red when there were seven hooks. `useHouseholdMembers.ts` calls the plain `refetchAfterWrite` and reports no `isPending` from it, so it is not in that file.

**`mutate` sites are affected too — benignly.** They are not a separate code path: `useMutation` returns `mutate = (vars, opts) => observer.mutate(vars, opts).catch(noop)` and `mutateAsync = observer.mutate` (`react-query@5.90.20/useMutation.js:31-40`), the same function. The caller does not await the result, but everything the mutation *reports* is deferred behind the same awaited `onSuccess`: `isPending` stays true (it reads `state.status`, set by the success dispatch) and the per-call `{ onSuccess }` fires from the observer's success notification, both now landing after the refetch. Three surfaces see it, and each is an improvement rather than a regression — they now settle against fresh data:
- `routes/settings/household/shelves/$shelfId/index.tsx:64,82` / `:85,92` — `updateShelf.mutate(…, { onSuccess: () => goBack() })`: navigation happens after the `['shelves']` refetch, and the Save button (`:119-120`, bound to `updateShelf.isPending`) keeps spinning until then.
- `routes/items/$id/relation/vendors.tsx:40` — `updateItem.mutate` with no per-call callback; the per-badge spinner and its `pointer-events-none` (`:77,81`) and the `useEffect` that clears `togglingVendorId` (`:28-29`) all key off `updateItem.isPending`, so the badge stays busy one refetch longer.
- `routes/items/$id/relation/recipes.tsx:45` — the same shape for `updateRecipe.isPending` (`:33-34,80,84`).

**Regression guards — only three of the five returns are pinned.** `useUpdateRecipe` (`RecipeDetailView.test.tsx`) and `useUpdateShelfMutation` (`ShelfDetailView.test.tsx`) each have a test that goes RED when the `return` is dropped; both hold the relevant refetch open behind a `vi.mock` gate on its `queryFn` (`getRecipes` / `getShelf` — note `getShelf`, not `listShelves`: gating the `['shelves']` list would leave `['shelves', id]` free to refetch, so the row would be gone before the assertion) and assert the group-action button is still disabled. `useApplyShelfFilterPicks` (`useApplyShelfFilterPicks.test.tsx`) has the same shape of guard: it holds `getAllItems` open behind a `vi.mock` gate and asserts `mutateAsync` has not resolved until that refetch lands. **`useUpdateItem` (`useItems.ts:436`) and `useAddItemToLocation` (`useItems.ts:349`) have no such guard** — verified 2026-08-27: dropping either `return` leaves the whole web suite green. Their search-tail consumers are `VendorDetailView`'s bucket-2 action and the wiring hook's bucket-3 action, so a gate test there would have to hold `getAllItems`/`getStockedItems` open. Do not read the paragraph above as implying all five are pinned.

- `useApplyShelfFilterPicks()` (`src/hooks/useApplyShelfFilterPicks.ts`) — PR D's mutation for joining a filter shelf from the search tail: applies a user's (or a single-option axis's default) per-axis picks to one item in one call. Takes `{ item, addTagIds, addVendorIds, recipe? }`. **Both branches are atomic (PR D-1, issue #269).** Local: `applyShelfFilterPicksBatch` (`db/operations.ts`), one Dexie `rw` transaction over `[db.items, db.recipes]` that re-reads both rows *inside* the transaction rather than trusting the caller's `item`/`recipe` (see the "Transactional batches" exception in `db/CLAUDE.md`) — a stale render closure can't double-append an id. The local branch's `onSuccess` **returns** its `['items']` + `['recipes']` invalidations, and the cloud branch awaits `refetchAfterWrite` over the same two queries (`{ query: GetItemsDocument }`, `{ query: GetRecipesDocument }`) — see the "Awaited invalidation" and "Reading again after a cloud write" paragraphs above.
