# Custom Hooks

**Navigation:**
- `useAppNavigation()` (`src/hooks/useAppNavigation.ts`) - Tracks navigation history in sessionStorage, provides `goBack()` function for smart back navigation to previous app page (fallback to home). Uses `router.history.push(previousUrl)` to preserve full URL (including search params) when going back.
- `useNavigationTracker()` (`src/hooks/useNavigationTracker.ts`) - Global hook (used in `__root.tsx`) that records every page visit as a full URL (`pathname + searchStr`) in sessionStorage. When params change on the same page, updates the last entry in place rather than appending a new one.

**Item List State:**
- `useUrlSearchAndFilters()` (`src/hooks/useUrlSearchAndFilters.ts`) - Manages search query, tag filter state, vendor/recipe filter state, and UI visibility (filters panel, tags visible) via URL params (`?q=`, `?f_<typeId>=`, `?f_vendor=id1,id2`, `?f_recipe=id1,id2`, `?filters=1`, `?tags=1`). Uses `router.history.replace` to update params in place (same history entry). Note: `filterState` only contains tag type filters — `vendor` and `recipe` keys are reserved and excluded from `filterState`. Exposes `selectedVendorIds: string[]`, `selectedRecipeIds: string[]`, `toggleVendorId(id)`, `toggleRecipeId(id)`, `clearVendorIds()`, `clearRecipeIds()`.
- `useSortFilter(storageKey)` (`src/hooks/useSortFilter.ts`) - Manages sort field and direction via localStorage key `${storageKey}-sort-prefs`. Used by all item list pages for per-page sort persistence. Accepts optional `defaultSortBy` option (defaults to `'name'`).
- `useScrollRestoration(key, scrollRef)` (`src/hooks/useScrollRestoration.ts`) - Saves/restores the scroll position of a scroll container element for a given key (typically the full URL). The app shell pins `<main>` to the viewport so the window never scrolls — list views scroll inside an inner `overflow-y-auto` container, so the hook operates on `scrollRef.current.scrollTop` / `.scrollTo`, not `window`. Saves scroll on component unmount (SPA navigation away); restores after data loads. Usage: attach a `useRef<HTMLDivElement>(null)` to the scroll container, call with `currentUrl` from `useRouterState` + the ref, then call `restoreScroll()` in a `useEffect` conditioned on `!isLoading`. For the 4 detail-page Items tabs (tags/vendors/recipes/shelves) the scroll container is owned by `LayoutInnerPages` and shared via `<Outlet>`; those callers read the ref from `useInnerPageScrollRef()` (a context exposed by `LayoutInnerPages`).

**Data Utilities:**
- `useVendorItemCounts()` (`src/hooks/useVendorItemCounts.ts`) - Returns `Map<vendorId, number>` of item counts per vendor, memoized with useMemo for performance
- `useTagItemCounts()` (`src/hooks/useTagItemCounts.ts`) - Returns `Map<tagId, number>` of global item counts per tag, memoized off `useItems()` + `useTags()`. Every tag gets an entry, including zeros. **Counts expand descendants** (`getTagAndDescendantIds`, the same walk `lib/shelfUtils.ts` uses): the shelf tag filter selects a tag *and all its descendants*, so a direct-assignment count would report 0 for a parent tag that in fact selects a dozen items. An item carrying both a parent and its child counts **once**. Location-unaware by design — these are global item↔tag relations. Distinct from the per-id `useItemCountByTag` (one async query per id, direct assignments only), which cannot be called in a badge loop.
- `useRecipeItemCounts()` (`src/hooks/useRecipeItemCounts.ts`) - Returns `Map<recipeId, number>` of global item counts per recipe, memoized off `useItems()` + `useRecipes()`. Every recipe gets an entry, including zeros. Recipes have no hierarchy, so membership is plain (mirrors the recipe branch of `lib/shelfUtils.ts`); counting from the item side also drops recipe entries pointing at deleted items. Location-unaware by design. The map-shaped counterpart to the per-id `useItemCountByRecipe`.
  - All three map-shaped count hooks are consumed together by the shelf filters tab (`settings/shelves/$shelfId/filters.tsx`), where each tag/vendor/recipe badge renders `` ` (${count})` `` after the name.
- `useItemSortData(items)` (`src/hooks/useItemSortData.ts`) - Returns `{ quantities, expiryDates, purchaseDates }` for sort operations on item lists. `quantities` is a `useMemo` (synchronous, no race condition). Local mode: `expiryDates` and `purchaseDates` are TanStack Query queries under the `['sort', ...]` key namespace. Cloud mode: uses `useLastPurchaseDatesQuery` (Apollo batch query) and derives expiry dates synchronously — no TanStack Query involved. Used by all five item list pages. Checkout explicitly invalidates `['sort', 'purchaseDates']` after purchase (local mode).
- `useItemLogs(itemId)` (`src/hooks/useInventoryLogs.ts`) - Returns inventory log entries for an item. Dual-mode: local uses TanStack Query + Dexie; cloud uses `useItemLogsQuery` (Apollo).
- `useAddInventoryLog()` (`src/hooks/useInventoryLogs.ts`) - Mutation hook to add an inventory log entry. Dual-mode: local calls `addInventoryLog` with the active location's id threaded in (matches the read side, `useItemLogs`, which filters by `activeLocationId`); cloud calls `useAddInventoryLogMutation` (Apollo).
- `useConsumeRecipes()` (`src/hooks/useRecipes.ts`) - Batch mutation hook for cooking done. Sends all item quantity updates, inventory logs, and recipe `lastCookedAt` stamps in a single call. Dual-mode: local uses `consumeRecipesBatch` (Dexie transaction); cloud calls `useConsumeRecipesMutation` (Apollo). Used exclusively by the cooking page `handleConfirmDone`.

**Shopping:**
- `useVendorCartCounts()` (`src/hooks/useVendorCartCounts.ts`) - Returns `Map<vendorId, { count: number; inactiveCount: number }>` for the `/shopping` index cards + the `'count'` sort. `count` is items with this vendor stocked in the **active location** (cloud: global, no location gate); `inactiveCount` is the subset with `targetQuantity === 0` (cloud: always 0). Distinct from `useVendorItemCounts()` below, which stays global/location-unaware for `/settings/vendors` — vendor management is location-independent, so the two pages showing different counts for the same vendor is expected, not a bug (see `apps/web/src/routes/CLAUDE.md`).
- `useVendorCart(vendorId: string | null)` (`src/hooks/useShoppingCart.ts`) - Gets the active cart for a specific vendor (null = "No vendor" cart). Local: TanStack Query keyed `['cart', 'vendor', vendorId]`; `getCart` is a pure read — carts are bootstrapped up front by `ActiveLocationProvider` (see `useActiveLocation()` below), not created lazily here. Cloud fallback: single active cart.
- `useAllActiveCarts()` (`src/hooks/useShoppingCart.ts`) - Returns all active carts (one per vendor). Local: TanStack Query keyed `['cart', 'all-active']`. Cloud fallback: single cart wrapped in array.
- `useLastPurchasedByVendor()` (`src/hooks/useShoppingCart.ts`) - Returns a `Map<string | null, Date | null>` of each vendor cart's `lastPurchasedAt` (the `null` key is the no-vendor cart). Drives the `'recent'` sort on the shopping index. **Dual-mode.** Local: TanStack Query keyed `['cart', 'last-purchased-by-vendor', { locationId }]`, reading the active location's carts and keying by `parseCartId`'s `vendorId`. Cloud: derived from the **same `useAllCartsQuery`** `useAllActiveCarts()` runs, so Apollo serves it from cache (no extra round trip) and `useCheckout()`'s existing `AllCartsDocument` refetch keeps it fresh. Cloud cart ids are **bare** (`'no-vendor'` / `<vendorId>`, no `${locationId}:` prefix), so the cloud branch keys on `cart.id` directly and maps `'no-vendor'` → `null` — `parseCartId` must not be used there.

**Cloud / Auth:**
- `usePostLoginMigration()` (`src/hooks/usePostLoginMigration.ts`) - Cloud mode only. Detects when a signed-in user has local IndexedDB items and has not been prompted before (localStorage `migration-prompted` key). Exposes `state: MigrationState`, `dismiss()`, and `importData(conflictResolution)`. `importData` calls `fetchLocalPayload()` then `importCloudData()` to migrate local data to cloud. Used by `PostLoginMigrationDialog`.

**Location:**
- `useLocations()` (`src/hooks/useLocations.ts`) - Returns all locations. Local-first only (no cloud GraphQL backend yet) — mode-independent. Also exposes `useCreateLocation`, `useUpdateLocation`, `useDeleteLocation`, `useReorderLocations`.
- `useActiveLocation()` (`src/hooks/useActiveLocation.tsx`) - React Context hook exposing `{ activeLocationId, setActiveLocationId, activeLocation }`. The active id is persisted in localStorage under `active-location-id` (`ACTIVE_LOCATION_STORAGE_KEY`), defaults to `DEFAULT_LOCATION_ID` (`'local'`), and falls back to the default if the stored id no longer matches any location (e.g. it was deleted). The provider `ActiveLocationProvider` is mounted in `__root.tsx` (wraps the whole app) and reads the location list via `useLocations`. It also bootstraps shopping carts: whenever `activeLocationId` changes (local mode only), it calls `bootstrapCarts(activeLocationId)` to ensure the no-vendor + per-vendor carts exist for that location, then invalidates `['cart']` queries so any cart query that resolved before the bootstrap finished refetches. This keeps `getCart` a pure read (see `db/operations.ts`) instead of lazily creating carts inside a `queryFn`. **LIVE (PR D):** the active location now scopes all stock-bearing data. Every data hook that reads/writes stock threads `activeLocationId` down to the operations layer (it appears in TanStack Query keys so switching the active location refetches): `useItems`/`useItem` (return a **joined `PantryItem`** = global `Item` + active-location `ItemStock` fields), `useLastPurchaseDate`, `useItemSortData`, `useItemLogs`, the cart hooks (`useVendorCart`/`useAllActiveCarts`/`useLastPurchasedByVendor` — carts are per `location × vendor`), `useCreateItem`/`useUpdateItem` (split the per-location stock STATE into the active-location `ItemStock`; the global stock configuration stays on the `Item` — see the v16 note in `db/CLAUDE.md`), `useConsumeRecipes` (cooking), and `useCreateVendor` (pre-creates the vendor cart for the active location). When no `ActiveLocationProvider` is mounted (isolated unit/story renders), the hook returns a fallback pinned to `DEFAULT_LOCATION_ID` with a no-op setter, so tests don't need to wrap in a provider.
- `useStockedItems()` (`src/hooks/useItems.ts`) - Returns the **pantry's** data source: only items that have an `ItemStock` in the **active location**, joined as `PantryItem[]` (via `getStockedItems`). Items not stocked in the active location are absent. Switching the active location re-scopes the result (the active id is in the query key `['items', 'stocked', { locationId }]`). All seven pantry views (`PantryListView` + the three group + three detail views) use this instead of `useItems`. Cloud mode falls back to the full cloud item list (ItemStock has no cloud backend yet). Contrast with `useItems()`, which returns **every** global `Item` joined with active-location stock (zeroed when not stocked) — used by the Add combobox catalog, cooking (to mark unavailable items), and shopping.
- `useItemSearchTail({ inGroupIds, query })` (`src/hooks/useItemSearchTail.ts`) - The shared tail behind every location-scoped item search. Reads the **global** catalog (`useItems()`), subtracts the ids the calling page already renders, and returns `{ inLocation, notStockedHere, hasExactGlobalMatch }`. `inLocation` is stocked in the active location but absent from the page's list; `notStockedHere` exists globally with no `ItemStock` here. **`inGroupIds` must be the page's own already-location-scoped list**, not raw group membership — an item carrying the group but stocked elsewhere belongs in `notStockedHere`, where one press stocks it here and promotes it straight into the page's list. `hasExactGlobalMatch` is true when any global item's name equals the query **including one already in the page's list**; callers pass it to `ItemListToolbar`'s `hasExactMatch` so the create affordance keys off the global catalog rather than the twice-filtered visible set — that is the #245 fix. **Cloud has ONE isolated bypass** (no `ItemStock` backend, so no item carries a `stockId`): every out-of-list match lands in `inLocation` and `notStockedHere` stays empty. Deleting that branch is what turns the third section on once cloud gains `ItemStock`. Memoize `inGroupIds` at the call site. **Callers should reach for `useItemSearchTailWiring` below instead of calling this directly** — it wraps this hook plus the view-agnostic wiring every page needs. **`useItems()` is called from inside this hook, not passed in as a parameter** — a deliberate PR B decision (carried forward from PR A's review). The obvious alternative, taking `items` from the caller, looked like it would save a redundant read on the pantry surfaces (which already call `useStockedItems()`), but it is actively wrong: the only list a pantry caller has to hand is the **stocked-here** set, and feeding that in as the "global catalog" would silently empty bucket 3 — exactly the location-blindness this feature exists to fix. The read this hook performs is also not redundant in practice: TanStack Query dedupes on the `['items']` key, and both `NewItemDialog` (mounted on the flat pantry) and the pantry views themselves already keep that query warm, so the extra call costs nothing measurable — shelf detail is the only surface that gains a genuinely new `getAllItems()` read per visit, the same read its sibling flat-pantry view already pays.
- `useItemSearchTailWiring({ inGroupIds, query, renderItem, sortTail?, groupAction?, groupNote? })` (`src/hooks/useItemSearchTailWiring.tsx`) - The shared VIEW-AGNOSTIC wiring behind every page's `ItemSearchTail` (extracted in PR B from the shopping cart page, which was the only caller until then; `PantryListView` and `ShelfDetailView` are PR B's two new callers; `VendorDetailView` and `RecipeDetailView` joined in PR C, completing the five surfaces — `shopping/$vendorId` plus those four). Calls `useItemSearchTail` for the two buckets, then: (1) owns the one-mutation-at-a-time pending id (`useState<string | null>`), injecting it into both action descriptors so a caller cannot forget it; (2) wraps a caller's `ItemSearchTailGroupAction.onAction` — **async**, `(item) => Promise<void>` — as `setPending(item.id); try { await onAction(item) } catch {} finally { setPending(null) }`, so pending clears regardless of outcome and callers use `mutateAsync` instead of hand-writing `{ onSuccess: clear, onError: clear }` pairs; (3) builds bucket 3's `addToLocationAction` itself (label `items.searchTail.addToLocation`, icon `<Plus />`, `onAction` calling `useAddItemToLocation().mutateAsync`), gated on `canAddToLocation = !isCloud && !!activeLocation` (mirrors the `mode === 'local'` guard every local-only mutation hook needs at its call site — see `useAddItemToLocation` above — and is not a second copy of `useItemSearchTail`'s own isolated cloud bypass in its location-scoping derivation) — and omits the key entirely (not a disabled action) when false; (4) applies the caller's `sortTail` to both buckets, or passes `useItemSearchTail`'s name order through unchanged if omitted. Returns `{ tailProps, hasTail, hasExactGlobalMatch }` — `tailProps` is a complete `ItemSearchTailProps`, spreadable straight into `<ItemSearchTail>`; `hasTail` is `hasVisibleTail(tailProps)` (exported from `ItemSearchTail.tsx`), the SAME derivation the component uses for its own early return, so a caller's empty-state guard and the component's suppression can never drift apart the way two independently-written booleans could. Bucket 2's `groupAction`/`groupNote` choice is NOT this hook's job — the calling page decides which one (or neither) to pass, e.g. the cart page passes `groupNote` for the no-vendor cart, `groupAction` once its vendor has resolved, and neither while the vendor id in the URL cannot be resolved (deleted-vendor window) — see `routes/CLAUDE.md`. `VendorDetailView` reproduces that same three-way split on the pantry side, and `RecipeDetailView` mirrors it for recipes.
- `useShowStock()` (`src/hooks/useShowStock.ts`) - Returns a `useCallback`-stable predicate `(item: { stockId?: string }) => boolean` = `isCloud || isStockedHere(item)`, the **display gate** every search-tail row renderer passes to `ItemCard`'s `showStock`. A bucket-3 row exists globally with **no** `ItemStock` in the active location, so `joinItemStock()` hands it zeroed quantities and no `stockId` — rendering those zeros as real stock is a lie. Cloud is the one exception: it has no `ItemStock` backend, so no cloud item ever carries a `stockId` and the gate would blank out every row; a cloud `Item` carries its stock inline and always shows it. That is **not** a second cloud path — it is the same one-line bypass its call sites already wrote out by hand. Extracted in PR C from three verbatim copies (`PantryListView`, `ShelfDetailView`, `shopping/$vendorId`) that PR C's own two new views would have taken to five. Re-exported from `hooks/index.ts`, but every call site imports the deep specifier `@/hooks/useShowStock` — purely to match how the same files import `useItemSearchTailWiring`; nothing forces it. **Deliberately NOT adopted at the four *filter* call sites** that write the same expression (`useVendorCartCounts.ts`, `routes/cooking.tsx`, `routes/shopping/index.tsx`, `routes/shopping/$vendorId.tsx`) — `.filter(showStock)` reads as nonsense where the caller is selecting rows, not deciding whether to show stock figures on one. Those want a separately-named predicate (`useIsStockedInActiveLocation()`) adopted at all four at once; that is its own change.
- `useAddItemToLocation()` (`src/hooks/useItems.ts`) - Mutation that stocks an existing global item in a location via copy-on-add (`addItemToLocation` — inherits `targetQuantity`/`refillThreshold`/`dueDate`, with packed/unpacked → 0; there is no configuration left on a row to copy since v16). Takes `{ itemId, locationId? }` — `locationId` defaults to the active location, and the Stock-tab pager passes the location of the page being viewed. No-op-safe: returns the existing row without resetting quantities if the item is already stocked there. Invalidates `['items']` + `['itemStocks']`, **returned from `onSuccess` so `mutateAsync` resolves only once both refetches have landed** (see the awaited-invalidation note below). **Local-mode only — throws in cloud mode** (cloud has no locations or `ItemStock`, so a stray call would write an orphan local row and report false success). Used by the pantry Add combobox's select-existing path and the Stock tab's "Add to location" CTA.
- `useRemoveItemFromLocation()` (`src/hooks/useItems.ts`) - Mutation that un-stocks an item from a location (`removeItemFromLocation`), cascading that location's inventory logs and its entries in that location's carts. Takes `{ itemId, locationId? }` — `locationId` defaults to the active location, and the Stock-tab pager passes the location of the page being viewed. The global `Item` survives: an item removed from its last location becomes an **orphan**, hidden from the pantry (`getStockedItems` filters on `ItemStock`) but still in the Add combobox catalog (`getAllItems`) and re-addable via `useAddItemToLocation`. Invalidates every family the cascade touches — `['items']` (pantry list, item reads, the item's logs), `['itemStocks']`, `['cart']`, `['sort']`, `['inventoryLogs']` and `['cartItems']` (the two per-item counts) — so removing from the **active** location leaves the UI consistent without a reload. **Local-mode only — throws in cloud mode**; it is destructive and irreversible, so it refuses loudly rather than silently deleting local rows the cloud UI never reads. Components must still gate their own UI on `mode === 'local'` (the `NewItemDialog` pattern) — the hook guard is a safety net, not a substitute.
- `useCreateItem(options?)` (`src/hooks/useItems.ts`) - Creates a global `Item` and, by default, an `ItemStock` for it in the **active location** (`createItem(input, activeLocationId)`). Passing `{ catalogOnly: true }` skips that `ItemStock` write, so the item lands in the catalog and is stocked **nowhere** — an intentional orphan (`getAllItems` surfaces it with `ZERO_STOCK` and no `stockId`; `getStockedItems` and therefore the pantry exclude it). The opt-in exists because the four Settings assignment tabs (`settings/{shelves,vendors,recipes,tags}/…/items`) edit a *global* item↔entity relation and must not write location-scoped stock, while the pantry's Add flow (`NewItemDialog`) must keep stocking here — hence opt-in rather than a changed default. **All four tabs pass the option to this hook directly**; none of them goes through `NewItemDialog`, which no longer takes a `catalogOnly` prop. No-op in cloud mode, which has no `ItemStock` backend. **No caller passes `consumeAmount`** — a newly created item defaults to `1` in both modes (`createItem` in `db/operations.ts`, and the cloud `createItem` resolver), so it is valid on arrival and `ItemForm` opens it clean. The default lives in exactly those two places (one per data mode, which cannot share code); a call site that passes a literal would fork it. It was `0` between 2026-08-23 and 2026-08-24 — see `routes/settings/CLAUDE.md`.
- `useUpdateItem()` (`src/hooks/useItems.ts`) - Takes `{ id, updates, locationId? }`. In local mode the five per-location state fields (`packedQuantity`, `unpackedQuantity`, `targetQuantity`, `refillThreshold`, `dueDate`) are split into `locationId`'s `ItemStock` (defaulting to the active location) and everything else — identity **and** the eight global stock settings — is written to the `Item`, applying to every location at once; the Stock-tab pager passes the location of the page being viewed. Cloud mode ignores `locationId` — a cloud `Item` carries its stock inline. Invalidates `['items']` and `['itemStocks']` (it writes an `ItemStock` row, which the Stock pager reads back) — two keys, not the five the previous `onSuccess` wrote, because invalidation matches by **prefix**, so `['items']` already covers `['items', id]`, the per-tag/vendor counts, and both item lists (`useItems`, `useStockedItems`). Both are **returned from `onSuccess`**, so `mutateAsync` resolves only once the refetches have landed (see below).
- `useApplyUnitSwitch()` (`src/hooks/useItems.ts`) - Commits a unit switch as ONE Dexie transaction (`applyUnitSwitchBatch`): the `Item`'s global stock configuration, the converted quantities for **every** location, and the rewritten `defaultAmount` of every affected recipe. Takes `{ itemId, updates, locationId?, stockConversions, recipeUpdates }` — all arithmetic is the caller's, since the transaction may not await anything of its own. Invalidates every family it touched in one pass: `['items']` (+ `['items', id]` and the per-tag/vendor counts), `['itemStocks']`, `['recipes']` (+ `['recipes','itemCount']`) — a missed one shows up as a stale screen after a *successful* save, never as an error. **Local-mode only — throws in cloud mode**, which keeps the Info tab's sequential path (Apollo has no client-side transaction to borrow). Used exclusively by the Info tab's unit-switch confirmation.
- `useInventoryLogCountByItem(itemId, locationId?)` / `useCartItemCountByItem(itemId, locationId?)` (`src/hooks/useItems.ts`) - Per-item counts of the two families `removeItemFromLocation` cascades. Passing `locationId` scopes each count to exactly the rows a removal from that location would delete (logs with an absent `locationId` read as the default location; cart entries match on the parsed cart id); omitting it counts every location. The location is part of the query key, so the two scopes never share a cache entry. The Stock tab's remove confirmation uses the scoped form — an item-global count would over-report what is being deleted.
- `useItemStock(itemId, locationId?)` / `useItemStocks(itemId)` / `useItemStocksForLocation(locationId?)` (`src/hooks/useItemStocks.ts`) - Raw `ItemStock` row reads. `useItemStock` returns the single (item × location) stock (defaults to the active location); `useItemStocks` returns every location's stock for an item; `useItemStocksForLocation` returns all stocks in a location. **Local-first only** — `ItemStock` has no cloud GraphQL backend yet (cloud TODO). The joined stock that pages consume comes via `useItems`/`useItem`; these expose the underlying rows for callers that need them (e.g. the Stock-tab pager in a later phase).

**Awaited invalidation** — `useUpdateItem`, `useAddItemToLocation`, `useUpdateRecipe`, `useUpdateShelfMutation` and `useApplyShelfFilterPicks` (local branch only) **return** their `invalidateQueries` from the local `onSuccess` instead of firing and forgetting it; almost every other `onSuccess` in these hooks still fires and forgets. TanStack `await`s whatever `onSuccess` returns *before* it dispatches success (`query-core@5.90.20/mutation.js:123` — `await this.options.onSuccess?.(…)` sits above `#dispatch({ type: 'success' })`), so a caller's `await` resolves only once the refetch has landed, not merely once the write has. The search tail needs that: `useItemSearchTailWiring` re-enables every row in a `finally` after that `await`, and the recipe and shelf group actions append to an array captured from the render closure — re-enabled against stale data, two quick presses drop one. Each returns the fewest keys that cover the work, since invalidation matches by **prefix**. **Cloud branches are no longer uniformly asymmetric**: `useUpdateRecipe` and `useApplyShelfFilterPicks` both pass `awaitRefetchQueries`; `useUpdateItem`'s and `useUpdateShelfMutation`'s cloud branches do not.

**`mutate` sites are affected too — benignly.** They are not a separate code path: `useMutation` returns `mutate = (vars, opts) => observer.mutate(vars, opts).catch(noop)` and `mutateAsync = observer.mutate` (`react-query@5.90.20/useMutation.js:31-40`), the same function. The caller does not await the result, but everything the mutation *reports* is deferred behind the same awaited `onSuccess`: `isPending` stays true (it reads `state.status`, set by the success dispatch) and the per-call `{ onSuccess }` fires from the observer's success notification, both now landing after the refetch. Three surfaces see it, and each is an improvement rather than a regression — they now settle against fresh data:
- `routes/settings/shelves/$shelfId/index.tsx:64,82` / `:85,92` — `updateShelf.mutate(…, { onSuccess: () => goBack() })`: navigation happens after the `['shelves']` refetch, and the Save button (`:119-120`, bound to `updateShelf.isPending`) keeps spinning until then.
- `routes/items/$id/relation/vendors.tsx:40` — `updateItem.mutate` with no per-call callback; the per-badge spinner and its `pointer-events-none` (`:77,81`) and the `useEffect` that clears `togglingVendorId` (`:28-29`) all key off `updateItem.isPending`, so the badge stays busy one refetch longer.
- `routes/items/$id/relation/recipes.tsx:45` — the same shape for `updateRecipe.isPending` (`:33-34,80,84`).

**Regression guards — only three of the five returns are pinned.** `useUpdateRecipe` (`RecipeDetailView.test.tsx`) and `useUpdateShelfMutation` (`ShelfDetailView.test.tsx`) each have a test that goes RED when the `return` is dropped; both hold the relevant refetch open behind a `vi.mock` gate on its `queryFn` (`getRecipes` / `getShelf` — note `getShelf`, not `listShelves`: gating the `['shelves']` list would leave `['shelves', id]` free to refetch, so the row would be gone before the assertion) and assert the group-action button is still disabled. `useApplyShelfFilterPicks` (`useApplyShelfFilterPicks.test.tsx`) has the same shape of guard: it holds `getAllItems` open behind a `vi.mock` gate and asserts `mutateAsync` has not resolved until that refetch lands. **`useUpdateItem` (`useItems.ts:436`) and `useAddItemToLocation` (`useItems.ts:349`) have no such guard** — verified 2026-08-27: dropping either `return` leaves the whole web suite green. Their search-tail consumers are `VendorDetailView`'s bucket-2 action and the wiring hook's bucket-3 action, so a gate test there would have to hold `getAllItems`/`getStockedItems` open. Do not read the paragraph above as implying all five are pinned.

**Shelf:**

- `useShelfQuery(id)` (`src/hooks/useShelves.ts`) - Returns a single shelf by ID. Dual-mode.
- `useCreateShelfMutation()` / `useUpdateShelfMutation()` / `useDeleteShelfMutation()` (`src/hooks/useShelves.ts`) - CRUD mutations. Dual-mode.
- `useReorderShelvesMutation()` / `useReorderShelfItemsMutation()` (`src/hooks/useShelves.ts`) - Reorder mutations. Dual-mode.
- Note: `FilterConfig` only holds `tagIds`, `vendorIds`, `recipeIds`. Sort is handled globally via `useSortFilter`.
- `useApplyShelfFilterPicks()` (`src/hooks/useApplyShelfFilterPicks.ts`) — PR D's mutation for joining a filter shelf from the search tail: applies a user's (or a single-option axis's default) per-axis picks to one item in one call. Takes `{ item, addTagIds, addVendorIds, recipe? }`. **Both branches are atomic (PR D-1, issue #269).** Local: `applyShelfFilterPicksBatch` (`db/operations.ts`), one Dexie `rw` transaction over `[db.items, db.recipes]` that re-reads both rows *inside* the transaction rather than trusting the caller's `item`/`recipe` (see the "Transactional batches" exception in `db/CLAUDE.md`) — a stale render closure can't double-append an id. Cloud: a single `applyShelfFilterPicks` mutation whose resolver (`apps/server/src/resolvers/shelf.resolver.ts`) does both writes inside one `prisma.$transaction`, reading the current `Item` and `Recipe` rows and unioning the ids server-side — the same read-then-union idempotency as the local batch, so a duplicate call can't double-append an id there either. The local branch's `onSuccess` **returns** its `['items']` + `['recipes']` invalidations, and the cloud branch passes `awaitRefetchQueries: true` over the same two queries — see the "Awaited invalidation" paragraph above.
