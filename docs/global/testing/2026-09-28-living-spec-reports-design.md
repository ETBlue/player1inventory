# Design: Living Spec Reports (Step 1)

Date: 2026-09-28
Status: 🔲 Pending
Brainstorming: [2026-09-28-living-spec-reports-brainstorming.md](2026-09-28-living-spec-reports-brainstorming.md)

## Goal

Publish test results as public HTML pages that non-developers can read. This is step 1 of
four. It uses the built-in reports, so we can judge whether they are readable enough
before spending more effort (Allure, Given / When / Then steps, role names).

## What a reader gets

A public site at `spec.player1inventory.etblue.tw` with a landing page that links to:

| Page | Source | Content |
|---|---|---|
| Local mode | Playwright HTML report, `local` project | ~175 E2E tests, with steps |
| Cloud mode | Playwright HTML report, `cloud` project | ~96 E2E tests, with steps |
| Offline (PWA) | Playwright HTML report, `pwa` project | ~69 E2E tests, with steps |
| Feature tests | Vitest `html` reporter, filtered | the `user can …` / `user sees …` tests |

The landing page also shows the run date and the commit it was built from.

## Parts

### 1. Step helper — `e2e/pages/step.ts`

A function that each page-object constructor calls once. It wraps every `async` method
of the object in `test.step`:

- Step name: the method name turned into words, plus the arguments. `checkRecipe('Pasta')`
  becomes `Check recipe "Pasta"`.
- `{ box: true }`, so a failure points at the line in the test, not at the helper.
- Non-`async` methods (the `get…` methods that return a `Locator`) are not wrapped.
  Wrapping them would make them return a `Promise` and break every caller.
- A page-object method that calls another method gives nested steps. This is fine.

No spec file changes.

### 2. Vitest feature report

`vitest run -t "user (can|sees)" --reporter=html` with the output directory set to the
spec build folder. Needs `@vitest/ui` as a dev dependency of `apps/web`.

**Open risk, checked first in the plan:** how tests excluded by `-t` appear in the report.
If they appear as ~1,950 "skipped" rows, the report is not readable and we return to the
choice between this reporter and a small custom page.

Only `apps/web` is included. `apps/server` tests are resolver tests, not user-facing
behavior.

### 3. Playwright reports

`pnpm test:e2e:all` (`e2e/run-all.sh`) already writes one report per project. The build
script copies them into the spec build folder.

### 4. Landing page

One static `index.html`, generated by the build script, with the four links, the run
date and the commit SHA. Plain HTML and CSS, no framework.

### 5. Publish script — `pnpm spec:publish`

1. Run the Vitest feature report.
2. Run `pnpm test:e2e:all`.
3. Build the spec folder (reports + landing page).
4. `wrangler pages deploy <folder> --project-name <name>`.

It publishes **even when tests fail**. A failing test is information the reader should
see, not a reason to hide the page. The script still exits non-zero at the end, so a
caller can tell.

A separate `pnpm spec:build` does steps 1–3 without uploading, for a local look.

The later CI job (not in step 1) will call the same script.

### 6. Hosting

A new Cloudflare Pages project, direct upload, public. The user creates it and the custom
domain once in the Cloudflare dashboard, and logs in with `wrangler login`.

## Out of scope for step 1

- Allure (step 2)
- Given / When / Then `test.step` blocks in specs (step 3)
- Role names in tests (step 4, with RBAC)
- CI
- `apps/server` tests in the report

## Risks

| Risk | What we do |
|---|---|
| Vitest report shows filtered tests as skipped | Checked in the first plan task, before building on it |
| Auto step names read badly | Add a name override for those methods later |
| Screenshots show only on failure today | Check Playwright's `screenshot` setting; `'on'` makes the report heavier. Decide in the plan |
| The report goes stale | Known until CI exists. The landing page shows the run date so a reader can see it |
